## 0. 先读这一页（TL;DR）

### 0.1 一句话说清这个比赛

一台阿克曼底盘小车，先在**识别板一**读 4 个二维码，知道"体检区 A/B/C 哪几个窗口有样本、这单要送到化验区 1~4 号哪个窗口"；
再去 A/B/C 取样本（**必须整车进框并停稳 1~2 秒**）、**语音播报**；
然后去**识别板二**读文字牌（"化验区空闲中，请快速通过" 或 "化验区忙碌中，需等待 n 秒"），照做并播报；
最后把样本送到对应化验窗口、进框停稳、播报样本数；
全程通过局域网把速度/位置/识别结果/当前任务发给裁判软件计分。**4 分钟内圈数越多、越准、越不漏播报，分越高。**
（注意：**我们练习用的裁判软件是 3 分钟**，与官方 4 分钟不同，见 §15 第 15 条。）

### 0.2 十条最贵的话（都是踩出来的）

1. **认车不要认"车号"，要认 IP + 主机名 + 账号 + ROS 版本**。这台队里被同时叫过"二号车"和"三号车"，见 §2。
2. **两台车的 `iscc pre` 语义完全不同**：ROS 1 车的 `pre` 一条龙直接发车；ROS 2 车的 `pre` 只是热车，**不敲 `iscc start` 车不会动**。
3. **改任何文件前先 `cp -p` 备份，改完立刻 git 提交并 push**。仓库长期有 100+ 脏文件，**永远不要 `git add -A`**。
4. **相机链路是整个系统最脆的一环**：ROS 1 靠 OpenNI/Astra 出 `mono8`；ROS 2 靠 `openni2-camera → mono8-relay`。QR 节点**写死要 `mono8`**，上游发 `rgb8` 会"不报错但识别不出来"。
5. **ROS 2 车上有三类系统性定时炸弹**：Fast DDS 共享内存泄漏、无 RTC 导致的时钟跳变、QoS 不匹配。它们的共同表现都是"节点在、话题有、就是没数据"。
6. **静止时 `/amcl_pose` 可能不更新**，限速节点会因此判超时；**RViz 看不到激光/地图，先怀疑跨机 DDS 和时钟，不要先改参数**。
7. **电池低于 ~11 V 就会出各种离奇失败**（"Failed to make progress"、中途掉电重启）。跑之前先看电压。
8. **判据要可量化**：二维码要够大（约 ≥55 px 可解、≥80 px 稳），到点要 `fine_xy 0.15 m / coarse 0.22 m`，限速要看"距离→速度"表，不要凭"看起来变慢了"。
9. **一次只改一个变量，改完必须实车验证**。"提交了"≠"解决了"。
10. **比赛日先确认三件事**：车能动、相机有图、裁判连上。这三件都通了再谈跑得快。

### 0.4 本笔记的操作边界（重要）

编写这份笔记期间，对两辆车**只做只读操作**，没有改动任何代码/配置。

| 允许（只读） | 本轮没做，也不该随手做 |
|---|---|
| `cat` / `ls` / `strings` / `systemctl cat` / `is-active` | 改任何文件（`sed -i`、`cp` 覆盖、`git add/commit`） |
| `lsblk` / `df` / `free` / `ps` / `ip` / `nmcli con show` | `mount` / `umount` / `mkfs` / `dd` |
| `ros2 node list` / `topic list` / `topic hz` / `echo --once` | `systemctl start/stop/restart`、`ros2 param set`、发 goal、发 `/cmd_vel` |

**队规建议（写下来，别只在口头）**
1. 任何一台车上的代码：**先 `git pull --rebase` 看差异 → 改 → 立刻提交并 push**（§13.5）。车上仓库里有 100+ 历史脏文件，**永远不要 `git add -A`**。
2. 改网络 / 挂 SD 卡 / 换 IMU 之前，**先在纸上写"回滚命令"**，并保证有一条不依赖 SSH 的退路（网线、键鼠、或"定时自动回滚"，见 §18.3）。
3. **SD 卡一律只读挂载**（`mount -o ro`），看完立刻 `umount`。卡里是另一台车的根文件系统，写坏了那台车就开不了机（§19.4）。
4. **只读诊断也会产生副作用**：`ros2 topic hz` / `echo` 会建立订阅者（可能唤醒相机/雷达多发数据），`ros2 param get` 会在参数服务上留记录。连着车做诊断时，心里有数即可，不必紧张，但**别把诊断脚本挂着跑一整晚**。

## 1. 比赛是什么

### 1.1 官方规则（来源：`智慧药房(1)\智慧药房\CRAIC2026-比赛规则-线下--智慧药房.pdf`，共 10 页）

| 项 | 内容 |
|---|---|
| 赛事 | 第二十八届中国机器人及人工智能大赛 · 机器人任务挑战赛 · **智慧药房**（线下） |
| 场地 | **4.9 m × 3.8 m** 不规则多边形，挡板围成；分**体检区**与**化验区**，另有**识别板一**、**识别板二**两个识别区 |
| 体检区 | A、B、C 三个窗口。每个窗口随机产生四种样本之一：静脉血 / 唾液 / 组织 / 血浆 |
| 化验区 | 1、2、3、4 四个窗口，分别对应：①血常规 → 静脉血 ②体液 → 唾液 ③免疫检测 → 组织 ④激素检验 → 血浆 |
| 识别板一 | 4 个方框（代表化验区 4 个窗口），**框里贴二维码**。二维码内容 = 体检区哪些窗口有样本（A/B/C/AB/AC/BC/ABC）。**每分钟更新 2 个** |
| 识别板二 | 文字牌，两种：`化验区空闲中，请快速通过` / `化验区忙碌中，需等待 n 秒`（n = 5~10） |
| 车体尺寸 | 垂直投影 **≥ 270 mm × 210 mm**，高度 **140~250 mm** |
| 算力上限 | CPU ≤ 4 核 1.5 GHz；GPU/BPU ≤ 5T(INT8) / 0.5T(FP16)；内存 ≤ 4 GB；系统 ≥ Ubuntu 18.04；框架 ROS1/ROS2；**底盘必须阿克曼** |
| 比赛时间 | **4 分钟**，无人干预，自主跑到跑不动为止；时间内试跑次数不限，取最高分那一轮 |
| 计分 | 场地分 100 分制，与技术报告 **7 : 3** 合成总成绩 |

**规则里的加减分（原文）**

| 项 | 分值 |
|---|---|
| 一次性送完一个二维码的全部样本 | 三个一次性送达 +25；两个一次性 +15；一次送一个 +5 |
| 板二动作 + 播报正确 | +3 |
| 体检区/化验区每次播报 | +1 |
| 双车轮流配送 | 总分 × 1.5 |
| 状态信息实时上传裁判 | 速度 +5 / 里程计 +10 / 视觉识别 +10 / 位置 +10 / 当前任务 +5 |
| 碰撞障碍物或其它车 | **-2 / 次** |
| 进框 1~2 个轮子未停入 | **-2 / 次** |
| 进框 3~4 个轮子未停入 | **-4 / 次** |
| 某体检窗口样本堆积 > 3 个 | **每过 1 分钟 -2** |

> **初学者最容易忽略的一条**：规则明确写"获取样本和送达样品时均需**小车全部车身进入方框内，并有明显的停留，建议停留 1~2 s**"。代码里 `pickup_seconds` / `delivery_seconds` 默认就是 **1.5 s**（`F1_yaofang.py:60-61`），这不是随便定的。

### 1.2 我们实际在用的"练习口径"

要点：**官方规则 ≠ 我们裁判软件的实现**。裁判软件（`smart.exe`，见 §10）是队伍自己写来练兵的，分项更细、口径更严，但对不上官方文档。两套都要知道：

| 维度 | 官方规则 | 我们裁判软件 |
|---|---|---|
| 一轮时长 | 4 分钟 | 顶部小计时 0→3:00；底部整队总计时 3:00（`使用说明.txt:40-46`） |
| 送样得分 | 3 个 +25 / 2 个 +15 / 1 个 +5 | 单样本 8 分 / 一次两样本 12 分 / 一次三样本 18 分，**本组封顶 48** |
| 板二 | +3 | 每次正确 +4，**封顶 12** |
| 播报 | 每次 +1 | 取样播报 +2（封顶 6）、送样播报 +2（封顶 6） |
| MD5 核验 | 规则里没有 | 每圈 4 分 × 3 圈 = **12 分** |
| 双车加成 | ×1.5 | 未实现 |
| 总分 | 100 | 各分项相加后 `qMin(100, …)`，再减扣分 |

> 结论：**练习时按我们裁判软件的口径优化（它更细），比赛日按官方规则理解（它更粗）**。两者不冲突的地方是：进框要准、播报要全、识别要对、别撞墙。

### 1.3 一"圈"到底发生了什么（任务主线的物理顺序）

```
起点(home) 
  → 识别板一(board1)：停车 → 开识别 → 读 4 个二维码 → 选定一个任务
  → 体检区取样本：按 C → A → B 的顺序（只取任务要求的窗口）
  → 识别板二(board2)：停车 → 读文字牌 → 播报 → 空闲就直接过 / 忙碌就等 n 秒
  → 化验区送样(1~4 之一)：进框停稳 → 播报"到达X窗口，样本数为N"
  → 回起点(home) → 下一圈
```

一个二维码最多 3 个样本（ABC），一台车一圈最多带走 3 个，**8 个样本封顶**——这就是代码里 `max_samples: 8`、`max_rounds: 3` 的由来。

## 2. 车、编号、账号——先把"谁是谁"钉死

> 这一节是整份笔记的**地基**。队里过去两个月最大的时间浪费，就是把两台车的命令、参数、IP 互相抄错。

### 2.1 为什么"车号"会坑死人

现场至少有四套"编号"，而且互相不对应：

| 编号体系 | 取值 | 含义 | 在哪出现 |
|---|---|---|---|
| **人类口语** | 一号车 / 二号车 / 三号车 | 谁先买的、谁是队友的……纯口头约定 | 聊天、复盘文档 |
| **IP 末位** | `.21` / `.22` / `.24` | 网络地址最后一段 | `iscc.conf`、SSH、所有脚本 |
| **`iscc` 的 `CAR_ID`** | `24` / `25` | **不是"第几号车"**，是车型档位：24 → `ROBOT_TYPE=EPRobotV2.2`、`JUDGE_ID=2`；25 → `EPRobotV2.3`、`JUDGE_ID=1` | `pharmacy_stack_common.sh:22-26`；`iscc` 第 59-64 行 |
| **裁判软件里的 `id`** | `1` / `2` / … | 上报 JSON 里的 `id` 字段；但裁判实际**按来源 IP 认车**（`mainwindow.cpp:2073-2083` 用 `connectedCars` 以 IP 为键） | `judge_tcp.py:188` |

**最典型的坑**：看到 `iscc pre 24`，以为是"操作 24 号车"，实际含义是"按 EPRobotV2.2 车型 + 裁判 ID=2 启动"。而它连的车是 `ROBOT_IP` 指定的那台，跟 `24` 这个数字**没有任何关系**。

## 4. ROS 零基础速成（够用版）

> 这一节只讲"能读懂这套代码、能自己查问题"的最小集。想系统学，去看 ROS 官方教程；但**先把这 8 个概念吃透，你就能上手这台车**。

### 4.1 一句话理解 ROS

> ROS 不是操作系统，是**一套"让很多小程序互相传消息"的约定 + 工具**。
> 每个小程序叫**节点（node）**，它们通过**话题（topic）**广播/订阅数据，通过 **TF** 描述"谁在谁的什么位置"，通过 **launch** 一次性拉起一堆节点。

**关键心智**：ROS 里没有"主程序"这个概念。`F1 主控` 也只是个节点，它跟 `move_base`、`amcl` 是平级的，只是它负责"发号施令"。

### 4.2 七个必须懂的概念

| 概念 | 是什么 | 在车上长什么样 | 怎么查 |
|---|---|---|---|
| **node** | 一个进程 | `/base_control`、`/amcl`、`/nav_pharmacy` | `rosnode list` / `ros2 node list` |
| **topic** | 广播频道（发布/订阅，多对多） | `/odom`、`/scan`、`/cmd_vel` | `rostopic list` / `ros2 topic list` |
| **message** | 话题里的数据结构（有 `.msg` 定义） | `nav_msgs/Odometry`、`sensor_msgs/LaserScan` | `rostopic type /odom` |
| **service** | 请求-应答（一对一，同步） | `/write_state`（存 Cartographer 地图） | `rosservice list` |
| **action** | 长任务（可中途反馈、可取消） | `move_base`（导航就是这个） | `rostopic list \| grep status` |
| **tf** | 坐标变换树（带时间戳） | `map → odom → base_footprint → base_laser_link` | `rosrun tf tf_echo map base_footprint` |
| **param** | 参数服务器（全局键值） | `/nav_pharmacy/waypoints/C` | `rosparam get /nav_pharmacy` |
| **launch** | 启动脚本（XML / Python） | `robot_localization.launch` | — |

**再补两个 ROS 2 专属的**：
- **lifecycle node**：节点有 `unconfigured → inactive → active → finalized` 状态机，`nav2` 全家都是。`active [3]` 才是真的活着。
- **QoS**：见 §4.4，这是 ROS 2 最容易"玄学"的地方。

### 4.3 ROS 1 与 ROS 2 的关键区别（只列会咬人的）

| 维度 | ROS 1（`.24`） | ROS 2（`.22`） |
|---|---|---|
| 通信中间件 | 自研 TCPROS，靠 **roscore（master）** 牵线 | **DDS**（Fast DDS），**无 master**，靠发现协议自动找 |
| 找节点 | 先起 `roscore`，否则一切免谈 | 不用 master，但**要同 `ROS_DOMAIN_ID`**，否则互相看不见 |
| Python | **2.7**（`print` 语句、`unicode`） | 3.x |
| launch | XML（`.launch`） | Python（`.launch.py`）为主 |
| 参数 | 全局 `/param`，`rosparam` | 每节点 `declare_parameter`，`ros2 param` |
| 时间 | `/clock` + `rospy.Time` | 同，但 `use_sim_time` 语义更严 |
| 命令行 | `rostopic` / `rosnode` | `ros2 topic` / `ros2 node` |

> **最容易犯的错**：在 `.22` 上敲 `rostopic list`（不存在），或在 `.24` 上敲 `ros2 topic list`（不存在）。**先 `ls /opt/ros/` 看是 melodic 还是 lyrical。**

### 4.4 QoS：为什么"话题存在但收不到"

ROS 2 的每个发布者/订阅者都带一组 **QoS 策略**，其中两个最关键：

| 策略 | 取值 | 含义 |
|---|---|---|
| **Reliability** | `RELIABLE`（默认） / `BEST_EFFORT` | RELIABLE 会重传；BEST_EFFORT 丢了就丢了（图像/雷达通常用它） |
| **Durability** | `VOLATILE`（默认） / `TRANSIENT_LOCAL` | TRANSIENT_LOCAL 会给"后来的订阅者"补发最后一帧（锁存） |

**兼容规则**：发布者 `BEST_EFFORT` + 订阅者 `RELIABLE` = **不兼容，收不到任何消息，且不报错**（只会在 `ros2 topic info -v` 里显示 incompatible）。

实战三条：
1. 看图/雷达/电池这类 `BEST_EFFORT` 话题，命令行一定要加 `--qos-reliability best_effort`：
   ```bash
   ros2 topic hz /camera/rgb/image_raw --qos-reliability best_effort
   ros2 topic echo --once /battery_state --qos-reliability best_effort
   ```
2. 锁存话题（比如 `/pharmacy/mission_status`、`goal_checker_selector`）订阅端必须 `TRANSIENT_LOCAL`，否则"晚启动的节点永远收不到"。
3. **`ros2 topic hz` 自己就是一个订阅者**。用它测"空闲时相机有没有出图"会自己唤醒相机，测出来的不是空闲状态（这个坑在 2026-10-27 踩过，见 `ISCC_会话复盘_20261113.md:876-881`）。

### 4.5 TF：整台车的"骨架"

TF 是一棵树，每个节点是"父子坐标系 + 平移 + 旋转 + 时间戳"。这台车的树长这样：

```
map
 └─ odom                      ← AMCL 或 Cartographer 发（只许一方！）
     └─ base_footprint        ← EKF 发（ROS1）/ eprobot-base 发（ROS2）
         └─ base_link         ← 静态 TF（(0,0,0)）
             ├─ base_laser_link  (0.14, 0, 0.11)
             ├─ base_imu_Link    (0.08, 0, 0)
             └─ camera_link      (0.14, 0, 0.11)
```

**三条铁律**
1. **同一条边只能有一个发布者**。两个都发 = 位姿来回跳（表现为"雷达图旋转/漂移、车在两点间抽搐"）。
2. **`map→odom` 属于定位模块**（AMCL 或 Cartographer），**`odom→base_footprint` 属于里程计**（EKF/驱动）。
3. **跨机看 TF 大概率缺环**。从 Windows/WSL 看 RViz 时，`map→base_footprint` 常常拿不到——**判断车况请以车上日志为准，别信远程 RViz**。

**常用命令**
```bash
# ROS1
rosrun tf tf_echo map base_footprint
rosrun tf view_frames           # 生成 frames.pdf，看整棵树

# ROS2
ros2 run tf2_ros tf2_echo map base_link
ros2 topic echo /tf --once
```

### 4.7 rosbag：事后复盘唯一的证据

```bash
# ROS1 车上（脚本已封装好 21 个话题）
bash ~/car_bag.sh nav
# 产物：~/bags/nav_<时间戳>/nav_<时间戳>.bag + rosbag_stdout.log
```

**看包技巧**
- 想确认"是不是算法的问题"，先看 `/cmd_vel` 有没有输出：有输出但车不动 → 底盘/串口；没输出 → 规划/任务。
- 想确认"定位有没有跳"，看 `/amcl_pose` 和 `map→odom` 的时间序列。
- `rosbag info` 里 `messages` 数量 ÷ 时长 = 实际频率，比 `rostopic hz` 更可靠（后者受网络影响）。

### 4.8 怎么读一次崩溃日志

按"从下往上、由内到外"读：

```
[ERROR] [1700000000.123] [controller_server]: Failed to make progress
```
↑ 这是**表象**，不是原因。往下游找：

| 表象 | 往哪看 | 常见真因 |
|---|---|---|
| `Failed to make progress` | `/odom` 频率、电池电压 | 电压低、轮子打滑、卡住 |
| `Timed out waiting for transform from base_link to map` | `/scan` Publisher count、AMCL 是否 active | 雷达无数据 → 没有 `map→odom` |
| `Failed to bring up all requested nodes` | `journalctl -u eprobot-nav` 前 30 行 | 启动竞态（TF 未就绪）、costmap 配置非法 |
| `Message Filter dropping message ... queue is full` | 车/主机时钟差 | 时钟不同步（见 §11.5） |
| `error_code:207`（BT action client timed out） | 同时段的 planner/controller 日志 | **多因**：规划超时、CPU 抖动、上层疯狂重试 |
| `Image buffer is corrupt. Size is 371790 (!= 921600)` | USB 带宽 / 相机参数 | USB2.0 丢包，或加了无效的 `color_mode` |
| `Failed init_port fastdds_port7013` | `/dev/shm` 里的 `fastdds_*` 数量 | SHM 泄漏 |
| `QR scan: candidates=0` | 图像编码是否 mono8、码有多大 | 编码不对 / 码太小 / 曝光过曝 |

> **经验**：ROS 日志里 `[ERROR]` 90% 是症状。真正的根因通常在**更早的 200 行**，或者在另一个节点的日志里。

### 5.2 底盘驱动：**实际跑的是 C++ 节点，不是 Python 脚本**

这是本笔记最重要的一处纠错。很多文档（含 `AGENTS.md`）说"第 41 行启动 `art_racecar.py`"，**不对**：

```xml
<!-- robot_navigation/launch/robot_lidar.launch:41 -->
<node pkg="eprobot_start" type="art_racecar_node" name="base_control" output="screen">
```

| 文件 | 行数 | 角色 |
|---|---|---|
| `eprobot_start/src/art_racecar_node.cpp` + `include/eprobot_start/art_protocol.hpp` | 922 + 474 | **真正在跑的 C++ 驱动** |
| `eprobot_start/script/art_racecar.py` | **1009** | **参考实现 / 测试基准**（CMakeLists:38,43 用它做 `--reference` 逐帧比对） |

好在这两份**帧格式、单位、积分公式逐条一致**，所以读 Python 版来理解逻辑是有效的；但**改 Python 版不会改变实车行为**，改 C++ 才生效。

### 5.3 串口协议（上位机 ↔ STM32）

#### 帧格式

```
┌──────┬─────┬─────┬─────┬──────────────┬──────┬──────┐
│ 0x5A │ LEN │ ID  │ CMD │    DATA...   │ 预留 │ CRC8 │
└──────┴─────┴─────┴─────┴──────────────┴──────┴──────┘
 帧头   整帧  固定   命令   载荷            NC    校验
        长度  0x01
```

- `LEN` = **整帧字节数（含 CRC）**；
- **CRC-8/MAXIM**：poly `0x31`（反射实现 `0x8C`），init `0x00`，xorout `0x00`；
- **覆盖范围（关键坑）**：
  - **下行（上位机→下位机）**：CRC 覆盖 `5A` 到 **NC（含）**，即 `crc8(frame[:-1])`；
  - **上行（下位机→上位机）**：CRC 覆盖 `5A` 到 **最后一个 DATA**，即 `crc8(frame[:-2])`，**NC 不参与**。
  - 这一点 `AGENTS.md` §4.2 写"CRC 覆盖到预留位（含）"，**对上行是错的**。上游脚本里 `0x0A` 的预留位恒为 `0xE8`，用它算 CRC 永远不对。
- `CRC == 0xFF` 时下位机跳过校验。

#### 命令表（2026-10-14 实机逐字节确认）

**上位机 → 下位机**

| CMD | 总长 | 用途 | DATA 布局 | 单位 |
|---|---|---|---|---|
| `0x01` | 18 | 速度 + 转向 + PID | `vx(2) vy(2) steer(2) kp(2) ki(2) kd(2) NC(1)` 大端 int16 | vx/vy mm/s；steer **mrad**；PID ×10 |
| `0x03` | 6 | 查询运动反馈 | 无 | — |
| `0x07` | 6 | 查询电池 | 无 | — |
| `0x09` | 7 | **设雷达档位 + 触发里程回包** | `mode(1) NC(1)`，1=Express 2=Boost 3=Standard | — |
| `0x13` | 6 | 查询原始 IMU | 无 | — |
| `0x21` | 28 | 上报树莓派状态 | CPU/内存/磁盘/IP | ×100 / ×10 / MB / GB |

**下位机 → 上位机**

| CMD | 总长 | 触发 | 解析 | 单位 |
|---|---|---|---|---|
| `0x0A` | 12 | `0x09` | `vx yaw ω` 三个 int16 | vx mm/s；yaw **0.01°**；ω **0.01 °/s** |
| `0x08` | 10 | `0x07` | `电压 电流 NC` | mV / mA（**电流恒 0**，板上没采样） |
| `0x14` | 38 | `0x13` | `gyro×3(i32) accel×3(i32) quat×4(i16)` | gyro `deg/s×1e5`；accel `mm/s²×1e5`；quat `×1e4` |
| `0x04` | 12 | `0x03` | `vx pwm steer NC` | — |

**六条实战结论**
1. **底盘严格"请求-应答"，绝不主动上报**。空口监听 6 秒收 0 字节；发一次 `0x09` 只回一帧 `0x0A`。驱动靠 50 Hz 反复发才把 `/odom` 拉到 50 Hz。
2. `0x0A` 的 **ω 单位是 deg/s × 100**（固件 `sensor.Gyro_deg.z*100`），不是 rad/s×1000。旧文档是错的。
3. `0x01` 第三字段是**转向角（rad → mrad）**，不是角速度。上位机先 `δ = atan(L·ω / v)` 换算再发。
4. **`0x0A` 的 yaw 与 ω 符号相反**。所以 launch 里钉死 `yaw_sign=-1`（yaw 取负）、`gyro_sign=+1`（ω 取正）。只用一个符号一定错一边（§5.4）。
5. `/imu_data` 的 `linear_acceleration_covariance[0] = -1`，意思是"**我没有加速度数据**"。谁想用加速度，得去订阅 `/imu/data_raw`（`0x14`，C++ 驱动 10 Hz 发）。
6. 低速有个"粘滞补偿"：`vx` 非零但 < `min_nonzero_speed`（C++ 版 0.08 m/s；Python 版写死 0.1 m/s）时会被**抬到阈值**，否则车根本不动。

### 5.4 `/odom` 到底怎么算出来的（公式）

不是简单的 `x += v·cos(yaw)·dt`。它用"板载 yaw 差分当 ω + 精确常曲率（SE(2)）积分"：

```python
# art_racecar.py:405-416
turn = ω · dt
half = turn / 2
sinc = 1 - half²/6            if |half| < 1e-6
     = sin(half)/half          otherwise
x += kv · dt · sinc · (vx·cos(yaw + half) − vy·sin(yaw + half))
y += kv · dt · sinc · (vx·sin(yaw + half) + vy·cos(yaw + half))
yaw += turn
```

其中（`:431-452`）：
- `ω = wrap(yaw_k − yaw_{k−1}) / dt` —— **yaw 来自 `0x0A` 的绝对朝向**，差分得角速度；
- `vx = 0.5·(vx_k + vx_{k−1})` —— 相邻两帧平均；
- `kv = base_kv = 1.089` —— 里程标定（+8.9%），只缩放 x/y 和 `twist.linear.x`；
- 只有 `0 < dt ≤ 0.2 s` **且** `0 < 墙钟差 ≤ 0.2 s` 才积分，否则只更新 yaw（防时钟跳变把车"瞬移"）。

> **为什么值得抄**：这个公式在 ω≠0 时是**精确解**（弦长用 `sinc` 修正），比一阶欧拉积分准得多。低速大转角时差别很明显。

**`yaw_sign` / `gyro_sign` 的由来**（`:806-807`）
```python
self.samples.append((vx, self.yaw_sign * yaw, self.gyro_sign * gyro_z, stamp, now))
```
固件里 `yaw` 与 `ω` 符号相反。旧驱动只对 yaw 取负；rewrite 版一度只有一个 `yaw_sign` 同时乘两者，导致"要么转向反、要么 ω 反"。最终拆成两个独立符号：`yaw_sign=-1`、`gyro_sign=+1`。

### 6.3 `iscc pre` 到底做了什么（5 步，按顺序）

```
① sudo -n systemctl start --no-block eprobot-base eprobot-imu lslidar
   sudo -n systemctl stop  eprobot-slam              # 建图和导航互斥
        ↓

        ↓

```

**第 ④ 步是全车最重要的时序**：nav 必须在 `/odom` 有数据之后再 restart。否则 `global_costmap` 拿不到 TF → `Failed to bring up all requested nodes` → 整栈白起。

**判定"好了"的四个客观标志**
1. 服务表里该 active 的全是 `active`；
2. 日志出现 `Managed nodes are active`（比 `ros2 lifecycle get` 可靠，后者在 Pi 上启动 >5 s 还偶发看不到节点）；
3. `iscc status` 里 `--- image ---` 的 Publisher ≥1、Subscription ≥2；
4. 相机 `/camera/rgb/image_raw` 有帧（约 7~10 Hz）。

**⚠️ 已知脆弱点**：`wait_nav_active` 用 `journalctl --since '-5 min' | grep 'Managed nodes are active'`，**上一轮的旧日志会被当成本次成功**。所以要么先 `iscc kill`，要么人工确认时间戳。

1. **没有 `velocity_smoother`、没有 `collision_monitor`、没有 `waypoint_follower`、没有 `docking_server`**。参数文件里写了它们也没用——**没进 `node_names` 就不会被激活**。

> ⚠️ **注释与实现不符（会误导人）**：`nav2_bringup.launch.py:87-89` 的注释写"Picks free_yaw_goal_checker while nav_pharmacy drives to A (the C -> A leg has no reachable final heading)"，

> `free_yaw_targets` 改成 `["A"]` 再试（命令行改不生效，要改脚本或加参数）。

### 6.5 相机链：这台车最脆的地方

```
Astra S (2bc5:0402, USB2.0, 无 UVC)
   │  Orbbec OpenNI2 SDK（/opt/oni2-orbbec）
   ▼
openni2-camera.service
   ros2 run openni2_camera openni2_camera_driver
     -r __ns:=/camera -r rgb/image_raw:=color/image_raw
     -p depth_registration:=false -p auto_exposure:=true
   ▼
/camera/color/image_raw   (rgb8 640x480, 921600 B)
   ▼
mono8-relay.service（C++，/home/keyuan22/relay_ws，max_fps 10）
   ▼
/camera/rgb/image_raw     (mono8 640x480, 307200 B, ~7.6 Hz)
   ├──► /detect_qrcode     （QR，写死 mono8）
   └──► /pharmacy_board2   （板二）
```

**六个必知坑**

1. **Astra S 没有 UVC，没有 `/dev/video0`**。任何 `v4l2_camera`、`camera.launch.py`、`camera.yaml` 的旧配置全部无效。真正生效的是 `openni2-camera.service`。
2. **绝对不要加 `-p color_mode:=VGA_15Hz`**。该模式名对这台驱动无效，会让**每一帧都损坏**（`Image buffer is corrupt. Size is 371790 (!= 921600)`），ROS 一张图都发不出去，QR 日志里连 `QR scan:` 都不出现。这是 2026-11-05 踩过的。
3. **QR 节点硬性要求 `mono8` + 话题名 `/camera/rgb/image_raw`**（二进制里写死）。所以必须有 relay，不能让相机直接发。
4. **`scp -r` 会把 `.so` 软链复制成 20 字节文本**（`file too short`）。要用 `ln -sf` 重建。
5. **相机只能被一个进程占用**。残留的 `ros2 launch` 会让服务版相机拿不到设备（`failed to claim usb interface ... BUSY`）。取流前 `pkill -f orbbec_as`，必要时 unbind/bind USB。
6. **`ros2 param set` 受用户隔离**。root 起的 `ros2 param set` 看不到 keyuan22 起的相机节点（DDS SHM 按用户隔离）。服务要用 `User=keyuan22` + `HOME=/home/keyuan22`。

**曝光**：现在服务里是 `auto_exposure:=true`（自动）。历史调参记录：`40` 时二维码边缘最锐利，`100` 能用，`400` 整片过曝。`iscc gray` 里可以用 `+/-` 现场调。

### 6.6 两个"外挂"Python 节点：限速与到点判据

这两个节点不在 Nav2 里，是 2026-11-05 之后加的，**改它们是调车最快的手段**。

#### `goal_speed_limit.py`：按"从哪到哪"限速

```python
target_speeds      = {"C>B": 0.20, "A>B": 0.12, "B": 0.15, "A": 0.22}
target_stop_radius = {"A>B": 0.65, "B": 0.45, "A": 0.35}
slow_radius = 0.9    # 进入这个距离开始减速
stop_radius = 0.35   # 这个距离内用 slow_speed
slow_speed  = 0.2
cruise_speed = 1.2
```

**键的构造与回退**：`key = f"{上一跳}>{目标}"`，取不到就取 `str(目标)`，再取不到用全局默认。
- 目标 B、上一跳 C → `C>B` = 0.20 m/s，stop 回落 `B` = 0.45 m
- 目标 B、上一跳 A → `A>B` = **0.12 m/s**，stop **0.65 m**（"蹭墙段"最慢）
- 目标 A → 没有 `B>A`/`C>A`，回落 `A` = 0.22 m/s，stop 0.35 m

**曲线**：`d ≥ slow_radius` → 发 0（不限速）；`d ≤ stop_radius` → `slow_speed`；中间线性插值到 `cruise_speed`。

**两个致命细节**（不修就"限速不生效"）
1. **QoS**：订阅 `/pharmacy/mission_status` 必须 `TRANSIENT_LOCAL`（lanched）+ `RELIABLE`；订阅 `/amcl_pose` 也要注意。
2. **`pose_timeout`**：AMCL 在**静止时不更新位姿**，1 s 超时就会让它直接发"不限速"。所以超时值要放大（曾改到 30 s）。

**怎么验证限速真的生效**：不要看"感觉慢了"。把车放在离目标 3.0 / 1.2 / 0.75 / 0.55 / 0.25 m 处，各读一次 `/speed_limit`，应该是 `0 / 0 / 0.96 / 0.65 / 0.25`。这个"距离扫描"法是 2026-11-06 发明的，比看日志可靠。

#### `goal_checker_bridge.py`：按航点切到点判据

订阅 `/pharmacy/mission_status`，当 `event=="navigating"` 且 `target ∈ free_yaw_targets` 时，向 `goal_checker_selector` 发 `free_yaw_goal_checker`，否则发 `general_goal_checker`。

**当前 `free_yaw_targets=[""]`（空哨兵）→ 永远选 general**，也就是说 A/B 点仍然要求 0.35 rad 朝向。想让某个点"到点不判朝向"，把它的名字加进这个列表即可（曾经对 B 用过，后来又回滚了）。

### 6.7 三类系统级地雷（这台车的"体质问题"）

#### 地雷 1：Fast DDS 共享内存泄漏

**现象**：节点在、话题有、`ros2 topic hz` 收到 0 帧；`Failed init_port fastdds_port7013`；CPU 飙高；`ros2 node list` 空。

**根因**：每个 DDS participant 会在 `/dev/shm` 建 `fastdds_*` 段。反复重启 + `Restart=on-failure` 会**越积越多**（实测积到 229 个），端口耗尽。

**处置**：
```bash
ls /dev/shm | grep -c fastdds     # 正常应是个位数
iscc clear                        # 轻量：只扫残留
iscc kill                         # 彻底：pkill → stop unit ×2 → rm /dev/shm/fastdds_* ×2
```
**顺序不能反**：必须**先 pkill 进程，再 stop unit**。反了的话 systemd 会把进程拉起来，立刻重建 SHM 段（实测清了 19 个又冒出 40 个）。

**根治**：所有 unit 加 `FASTDDS_BUILTIN_TRANSPORTS=UDPv4`（已经加了，`Failed init_port` 从"每几分钟一次"降到 0）。

#### 地雷 2：没有 RTC → 时钟跳变

**现象**：AMCL 丢掉全部扫描（`timestamp earlier than all data`）；RViz 刷 `Message Filter dropping message ... queue is full`；`tf` 拿不到对应时刻的变换。

**根因**：树莓派没有 RTC，开机时间从 0 或上次关机时间开始，chrony 一联网就**跳几十天**。历史上出现过一次 step 4.4e6 秒（51 天）。

**处置**：
```bash
timedatectl status | grep -E 'NTP|synchronized'   # 必须 yes/yes
chronyc tracking                                   # 看 System time / Stratum
date -u                                            # 与主机对比
```
**必须在 `eprobot-nav` 之前完成校时**。`iscc pre` 里已经加了"NTP 同步门禁"，但**改完时钟必须重开 RViz**（旧实例的缓冲已经乱了）。

#### 地雷 3：跨机 DDS 端点匹配不稳定

**现象**：同一台主机上，`/scan`（8 KB）能收到，`/scan_viz`（同样 8 KB）收不到；`/odom`（小包）也收不到。**看起来像丢包，其实不是**。

**结论**（2026-11-07 用"尺寸-到达对照实验"证伪了"大包必丢"）：这是 Fast DDS 跨机端点匹配的问题，不是带宽。

**处置**：远程 RViz **只作辅助**。真要跨机看得稳，要么给 Fast DDS 写 XML 指定网卡 + `initialPeersList`，要么就在车上跑 RViz + X11。**判断车况永远以车上日志和车上话题为准。**

## 7. 任务逻辑（F1 主控）

> 源码：`pharmacy_pkg/scripts/F1_yaofang.py`（675 行，ROS 1，Python 2.7）。
> ROS 2 车的 `f1_mission_node` **是同一套逻辑的 C++ 编译版**（节点名同为 `nav_pharmacy`，参数名、事件名、播报文案几乎逐字一致），只是**没有源码**，只能改 YAML。

### 7.1 主循环

```python
run():
    等 move_base（最多 60 s）
    等定位（map→base_footprint 的 TF，最多 8 s）
    deadline = now + match_seconds        # match_seconds=0 表示不限时
    while alive() and not complete():
        task = read_task()                # ① 去板一读任务
        if not run_round(task):           # ② 取药 → 板二 → 送样
            record('mission_aborted'); break
        if complete(): break
        move('home')                      # ③ 回起点，准备下一圈
```

`complete()` 的判据（`F1_yaofang.py:154-157`）：
```python
match_seconds > 0 and (completed_rounds >= max_rounds or delivered_sample_count >= max_samples)
```
默认 `max_rounds=3`、`max_samples=8`。**注意**：`match_seconds=0` 时这两个限制**完全失效**（连续练习模式）。

### 7.2 读板一（`read_task`）

```
move('board1')
  └ 首圈：先把 TEB 限到 max_vel_x=0.35 / acc_lim_x=0.5（防起步猛冲），结束后恢复 0.9/1.0
pause(0.5) → settle()                    # 必须停稳，否则图像糊
循环（直到成功或超时）：
    publish /detection_control = True
    publish /pharmacy/remaining_samples = 剩余容量
    publish /pharmacy/judge_cv1 = 'NONE'、judge_cv2 = ''
    等 /pharmacy/qr_report，最长 qr_timeout=5 s
        └ 期间每次醒来都播报已攒下的干扰样本
    成功 → 发 judge_cv2 = "ABC-3" → 语音播报"识别到任务二维码，ABC-3"
    超时 → 关探测 → move('qr_reposition') → move('board1') → 再试
```

**为什么要有 `qr_reposition`**：码太小/角度太斜时，停在原地重试没用，必须"退一点再进"换个视角。这个点默认是 `home` 与 `board1` 的中点，朝向同 `board1`。

### 7.3 一趟取送（`run_round`）

```
① 朝向策略：任务同时含 A 和 B → A/B 的 yaw 用 π/6（30°）；否则用 π/2（90°）
   只改 yaw，不改 x/y
② letters = 任务的字母串，按剩余容量截断
③ 取药顺序固定 'C' → 'A' → 'B'：
     普通情况：move(窗口) → pause(1.5 s)
     特殊情况：如果 A 之前已经取过 C，且存在 P 点：
              move_through('P')            # 不刹停地穿过 P
              reverse_to('A', P的yaw)      # 倒车进 A，保持朝向
              失败则 fallback 到 move('A')
④ 语音："取到A、B窗口中的静脉血样本"
⑤ pass_board2()：去板二 → 识别 → 播报 → 按 FREE/BUSY 行动
⑥ move(化验窗口) → pause(1.5 s) → 语音："到达血常规窗口，样本数为2"
⑦ 计数：delivered += len(picked)，rounds += 1
```

**为什么取药顺序是 C→A→B 而不是 A→B→C**：这是场地几何决定的。C 在最外侧（x=1.45）、A 在里侧（x≈0.65），从 C 到 A 需要掉头，而阿克曼最小转弯半径 0.30 m、通道宽度不够，所以设计了 `P` 点：**先开到 P（靠近 B 的位置），再直线倒进 A**，避免在狭窄处掉头。这一整套是 2026-10-26 的 `feat: add non-stop P transition and reverse into A` 提交引入的。

**`P` 点的算法**（`F1_yaofang.py:105-111`）
```python
p_yaw = π/6
P.x = (A.x + C.x)/2 + 0.40·cos(p_yaw)
P.y = 3.43
P.yaw = p_yaw
```
即"A、C 中点再往前 0.40 m"，`y=3.43` 固定在靠墙一侧。

### 7.4 板二（`pass_board2`）

```
move('board2') → settle()
若 board2_settle > 0：再等一会儿（默认 0，ROS2 车也是 0）
publish /pharmacy/board2_control = True
等 /pharmacy/board2_status，最长 board2_timeout（ROS1 6 s / ROS2 8 s）
    超时 → 直接当 FREE，记 board2_unrecognized_free
publish /pharmacy/judge_cv1 = "FREE" 或 "BUSY_8"
播报："化验区空闲中，请快速通过" / "化验区忙碌中，需等待8秒"
若 FREE：如果配了 board2_exit 就开过去，否则直接继续
若 BUSY：从"播报完成时刻"起等满 n 秒（注意：是从 last_speech_done 起算，不是从识别起算）
```

**两个隐蔽点**
1. **"未识别"= FREE**。这是代码里的硬编码兜底（`F1_yaofang.py:549`）。逻辑上"赌一把"，风险是板二其实 BUSY 却直接冲过去。
2. **等待时间从播报结束算**。因为规则要求"播报并等待相应时间"，裁判是听播报的。

### 7.6 失败路径：车卡住之后会发生什么

```
move(name) 失败/超时
  ├ 记录 navigation_failed / navigation_timeout
  ├ pause(1.0)
  └ 重试同一个目标（无限次，直到 match 超时或被 Ctrl-C）
        │
        └ 在 move_base/Nav2 内部还有一层恢复：
             ROS1: 清代价地图（保守 1 m / 激进 3 m）
             ROS2: BackUp 0.40 m → 清地图 → Wait 2 s，最多 6 次
```

**所以"车卡住不动"通常不是任务层的问题**，而是：
1. 目标点本身不可达（离墙 < 0.18 m）；
2. 定位飘了（`/amcl_pose` 跳到别处，路径规划从"当前位置"出发必然撞墙）；
3. 代价地图里有"幽灵障碍"（上一轮留下的、或人的腿）；
4. 电池低压导致轮子输出不足。

### 7.7 事件流：`mission.jsonl` 是你最好的朋友

每一条都是一行 JSON：

```json
{"event":"navigating","timestamp":1794572149.7,"rounds":0,"delivered":0,"target":"board1","attempt":1}
{"event":"qr_scanning","attempt":1,...}
{"event":"qr_accepted","cv2":"ABC-3","attempt":1,...}
{"event":"speech_started","id":"/home/.../run_1_xxx:1","text":"识别到任务二维码，ABC-3","kind":"board1_task"}
{"event":"speech_finished","status":"DONE",...}
{"event":"sample_picked","window":"C",...}
{"event":"board2_recognized","status":"BUSY_8","wait_seconds":8}
{"event":"delivery_completed","cv2":"ABC-3","actual_letters":"ABC",...}
```

**怎么用它定位问题**

| 你怀疑 | 查哪个 event | 判据 |
|---|---|---|
| 导航慢 | `navigating` → 下一个 event 的时间差 | 单段 > 8 s 就不正常 |
| 识别慢 | `qr_scanning` 到 `qr_accepted` | 正常 1~3 s；反复 `qr_timeout/qr_retry` 说明码太小/太糊 |
| 语音没播 | `speech_finished` 的 `status` | `DONE` 才算成功；`MISSING` = 没有对应 wav；`TIMEOUT` = 播放卡住 |
| 到点不准 | `navigation_failed` 的 `state` | 4=ABORTED、2=PREEMPTED、9=其他 |
| 整体崩了 | `mission_aborted` / `match_timeout` | 看它前一个 event 是什么 |

**文件位置**
- ROS 1：`~/robot_ws/.log/pharmacy/mission.jsonl`
- ROS 2：`~/.ros/pharmacy/mission.jsonl`

写日志的代码在 `record()`（`F1_yaofang.py:162-175`）：**每写一行都同时发 `/pharmacy/mission_status`**——这就是限速节点和 checker 桥的输入源。

## 8. 视觉：板一二维码与板二文字牌

### 8.1 板一：4 个二维码 → 5 个整数 → 窗口号

#### 物理布局

识别板一是 **2×2 四个方框**，每个框里一张二维码。解码后按几何排成 **[左上, 右上, 左下, 右下]**，下标 `target_area ∈ {0,1,2,3}`。

#### 编码规则

二维码的**原始内容只是一个字母串**（A/B/C 的任意非空子集，≤3 字符，不重复）。程序把它规范化成"按 ABC 顺序排"（例如 `BA` → `AB`），然后打包成 5 个整数：

| 下标 | 字段 | 含义 |
|---|---|---|
| `data[0]` | `c` | 含 `C` ? 1 : 0 |
| `data[1]` | `a` | 含 `A` ? 1 : 0 |
| `data[2]` | `b` | 含 `B` ? 1 : 0 |
| `data[3]` | `count` | `len(字母串)` |
| `data[4]` | `encoded` | **`6 - target_area`** ∈ {6,5,4,3} |

**窗口号换算**（`pharmacy_rules.py:7`）
```python
WINDOWS = {3:'4', 4:'3', 5:'2', 6:'1'}
window = WINDOWS[encoded] = 7 - encoded = target_area + 1
```

| 面板 | 位置 | `encoded` | **窗口** | 化验项目 | 对应样本 |
|---|---|---|---|---|---|
| 0 | 左上 | 6 | **1** | 血常规 | 静脉血 |
| 1 | 右上 | 5 | **2** | 体液 | 唾液 |
| 2 | 左下 | 4 | **3** | 免疫检测 | 组织 |
| 3 | 右下 | 3 | **4** | 激素检验 | 血浆 |

> **一句话**：**窗口号恒等于面板号（1~4）**，`encoded` 只是它的"倒序编号"。别被 `6-target` 这个写法绕晕。

**实例**：`areas=["A","AB","ABC","C"]`，选中 `target_area=2`（左下）的 `ABC` → `data=[1,1,1,3,4]` → `encoded=4` → **窗口 3（免疫检测 / 组织）** → `CV2 = "ABC-3"`。

#### 选哪一个

`build_result`（`detect_code_for_EPRobot.py:429-452`）的选择逻辑：
1. 只要"text 非空、不是 invalid、不在 `completed_qr` 里、长度 ≤ 剩余容量"的面板；
2. 在这些里选 **字母最多（text 最长）** 的那个。

**为什么选最长的**：`ABC` 一次能带 3 个样本，得分效率最高（裁判软件里 3 个一次 = 18 分，1 个 = 8 分）。

#### 识别参数（调它之前先知道这些）

| 参数 | 值 | 含义 |
|---|---|---|
| `scan_hz` | 5.0 | 扫描频率（不是帧率） |
| `MAX_DECODE_WIDTH` | 1440 | 宽 >1440 才缩放 |
| `MAX_CANDIDATES` | 12 | 单帧最多解 12 个候选 |
| `HISTORY_SIZE` / `REQUIRED_HITS` | 5 / **3** | **同一签名连续出现 3 次才确认** |
| 面板面积 | 图像的 1.5%~45% | 太小/太大都不当面板 |
| 面板宽高比 | 0.65~1.35 | |
| 面板占外接矩形比 | ≥0.80 | 判断"是不是规整的方框" |
| 网格 `coverage` | ≥0.002（0.2% 面积） | |
| 倾斜度 | ≤0.75 | |
| 尺寸离散度 | ≤2.0 | 四个面板大小不能差太多 |

**"连续 3 次"的副作用**：识别变慢（5 Hz × 3 = 至少 0.6 s），但误识率大幅下降。这是刻意的权衡。

#### 为什么必须 `mono8`（重点）

- Python 端：`bridge.imgmsg_to_cv2(frame, b'mono8')`（`:609`）
- C++ 端：`toCvShare(frame, "mono8")`，且 `if (depth != CV_8U) throw "QR decoder expects 8-bit image"`
- zbar 封装写死 `"Y800"`（单通道 8 bit）
- 话题名写死 `/camera/rgb/image_raw`

**上游发 `rgb8` 会怎样**：不报错、不崩溃、不产生任何 `QR scan` 之外的线索。异常被最外层 `except` 吞掉且 **5 秒节流**，日志里几乎看不到；`/pharmacy/qr_report` 永远不发，F1 只看到 `qr_timeout / qr_retry` 循环。**这就是"相机明明有图、就是识别不出来"的头号原因。**

#### 二维码要多大（唯一的硬指标）

没有"最小分辨率"代码约束，但有物理约束：`zxing` 在 **约 25 个模块、每模块 1.8 px** 时解不出来。实测经验值：

| 码宽 | 结果 |
|---|---|
| ~45 px | 解不出（`candidates=1~2, hits=0/3`） |
| **≥55 px** | 可解 |
| **≥80 px** | 稳定 |

对应到车上：**板一停车点要比"看起来够近"再近 10 cm**。`board1` 的 x 从 0.518 改到 0.618 就是为了这个（`AGENTS.md` §10.3 注释原话："stops 10 cm closer so the QR panels are big enough for zxing"）。

### 8.2 板二：三套后端，能力差别很大

| 维度 | `fixed`（C++ 模板） | `template`（Python 模板） | `rapidocr`（OCR） |
|---|---|---|---|
| 入口 | `pharmacy_board2_fast_node` | `board2_template_node.py` | `board2_detect.py` + `board2_worker.py` |
| 模板/模型 | `pass.png`、`wait8s.png` | `IDLE_*.png`、`BUSY_*.png`（2+2） | PP-OCRv4 ONNX |
| 判据 | 两行文字互相关 `0.45·上 + 0.55·下`，`min_score 0.72`、`min_margin 0.10`；BUSY_8 还要"8 字双孔"证据 ≥2/3 | 240×160 透视矫正 + 两行 160×28，`0.35·上 + 0.65·下`，`min_score 0.60` | 文本规则：含"等待/忙碌"→`BUSY_n`；含"空闲/通过"→`FREE` |
| **能输出的值** | **只有 `FREE` / `BUSY_8`** | **只有 `FREE` / `BUSY_8`** | **`FREE` 或 `BUSY_5`~`BUSY_10`** |
| 确认票数 | 连续 2 票（间隔 ≤0.5 s） | 4 帧窗口内 2 票 | 5 帧内 ≥`need`（默认 1） |

**三个必须知道的结论**
1. **`BUSY_5/6/7/9/10` 这 5 条语音，只有 `rapidocr` 后端才可能触发**。模板族永远只会说"需等待 8 秒"。如果比赛现场的板二显示"需等待 6 秒"，模板后端仍然会播 8 秒、等 8 秒——**动作错了，扣分**。
2. **`template` 后端会"编造"结果**：认不出来就返回 `fallback_state=FREE`。看起来"很稳"，其实是赌。
3. **`fixed` 后端有强拒识**（`min_primary_score 0.90` + 8 字专检），宁可不说话也不说错。**比赛用哪个后端，取决于你更怕"漏"还是更怕"错"。**

### 8.3 干扰样本

**定义**：二维码内容规范化失败（空串 / 长度>3 / 含 A、B、C 以外字符 / 字母重复）→ 标记 `invalid=True`，但**不丢弃**，保留原始字节和 MD5。

**怎么上报**
1. 随正常结果附带：`/pharmacy/qr_report` 里带 `interference: [{raw_base64, md5}]`；
2. 没有可用任务时单独发：`{"interference":[...]}`，同一 enable 周期只发一次。

**F1 怎么处理**：收进队列去重 → **每一条都单独播报"识别到干扰二维码"**（`rules_interference.wav`）→ 记进 MD5 证据表（`kind=interference`，`plain` 是原始字节的 UTF-8 解码）。

**注意**：干扰样本**不上报裁判**（`judge_tcp` 的 JSON 里没有这个字段），只进本地证据和语音。所以它的价值是"证明我识别到了并正确处理了"，属于技术报告/申诉材料，不是当场得分项。

## 9. 语音与证据链

### 9.1 播报链路

```
F1 主控 say(text, kind, plain, raw)
  ├ settle()：发零速直到 /odom 判定静止 ≥0.3 s（"车停稳了才说话"）
  ├ 等 /pharmacy/car_speech 有订阅者（最多 2 s）
  ├ publish {"id":"<证据目录>:<序号>","text":"..."}
  ▼
pharmacy_speech 节点
  ├ 用 text 去 speech_manifest.json 里查 wav 路径
  │    查不到 → MISSING（不播）
  ├ 队列（16）满了 → QUEUE_FULL
  ▼
paplay --device=<device> <wav>
  └ 失败 → aplay -q -D plughw:0,0 <wav> → aplay -q <wav>
  ▼
publish /pharmacy/speech_status {"id":..., "status": "PLAYING"/"DONE"/"FAILED"}
  ▼
F1 收到 DONE → 才继续（否则整轮中止！）
```

> 上图是 **ROS 1 Python 版（`F1_yaofang.py`）** 的链路。两台车实现不同，别混：
>
> | 车 | 谁真正发声 | 依据 |
> |---|---|---|
> | ROS 1 + `use_cpp:=true`（默认） | **F1 自己 `paplay`**，`competition.launch` **不起** speech 节点 | `competition.launch:27` 注释；`f1_mission_node.cpp:48-52,218-257` |
> | ROS 1 + `use_cpp:=false` | `pharmacy_speech` 节点（Python） | `competition.launch:39-44` |

**关键约束**

- ROS 2 车用 `aplay plughw:0,0`（headless 没有 PulseAudio）；ROS 1 车用 `paplay --device=alsa_output.platform-bcm2835_audio.analog-mono`。

### 9.3 MD5 证据表（裁判核验的依据）

每轮任务在 `~/robot_ws/.log/pharmacy/evidence/run_<时间戳>_<随机>/` 下生成 `records.jsonl` + `MD5.xlsx`。

**三张表**

| 表 | 内容 |
|---|---|
| `逐项记录` | 11 列：圈次 / 类型 / 明文 / 明文UTF-8 MD5 / 播报文字 / 播报UTF-8 MD5 / 播放状态 / 原始字节Base64 / 原始字节MD5 / 时间戳 / 编号 |
| `每圈汇总` | 4 列：圈次 / 口径（待裁判确认）/ 拼接明文（LF 换行，无末尾换行）/ UTF-8 MD5 |
| `口径说明` | 7 条免责说明 |

**每圈两行汇总**
1. **口径 A**：`kind ∈ {board1_task, interference, board2}` 的 `plain` 按顺序用 `\n` 连接 → MD5；
2. **口径 B**：该圈所有 `status=='DONE'` 的 `speech` 按顺序用 `\n` 连接 → MD5。

**算法**：`MD5(UTF-8(文本))` 的 32 位**大写**十六进制。

**表里自己写着的免责声明（很重要）**
- "板一保留实际选择的 ABC-1 形式；沿用现有样本编码，**不声明为官方映射**"
- "LF 拼接只是本程序的明确约定，**不代表官方模板**"
- "**不自动判分**，由裁判核验"

> 这三句话的意思是：**这张表是我们自己的证据，不是官方格式**。裁判可以拿它逐项核对，但"每圈汇总 MD5"必须由我方复算后再报。

## 10. 裁判系统

### 10.1 是什么

`D:\ISCC\裁判软件_复赛版_每分钟后台递补_20261024\smart.exe` —— 一个 **Qt5 写的 Windows 桌面程序**（附带完整 Qt 源码 `源码\mainwindow.cpp`，3083 行）。它做四件事：
1. **监听 TCP 8888**，收小车上报的 JSON；
2. 显示小车实时位置（地图上画轨迹）、速度、当前任务、CV1/CV2；
3. 裁判手动点按钮加分/扣分；
4. 导出 `比赛打分表_*.docx` 和 `score_template.docx`。

### 10.2 通信协议（这是最该背下来的）

**一行一个 JSON**，UTF-8，`\n` 结尾，TCP 长连接（断了自动重连）：

```json
{"id":"25","speed":0.42,"odom":[1.234,-0.567],"task":"ABC","CV1":"FREE","CV2":"ABC-3"}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 车号（字符串） |
| `speed` | float | 当前线速度绝对值 m/s（`abs(cmd_vel.linear.x)`） |
| `odom` | [x, y] | **`map` 坐标系**下的位置（优先 TF `map→base_footprint`，回退 `/amcl_pose`） |
| `task` | string | `A/B/C/AB/AC/BC/ABC` 之一，其他值一律发空串 |
| `CV1` | string | 板二结果（`FREE` / `BUSY_8`） |
| `CV2` | string | 板一结果（`字母-窗口`，如 `ABC-3`） |

**发送频率**：10 Hz（`rate: 10.0`）。
**发送方**：`judge_tcp.py` / `judge_tcp_node`。
**接收方**：裁判软件的 `QTcpServer`。

**四个容易踩的坑**
1. **裁判按来源 IP 认车**（`connectedCars` 以 IP 为键），不是按 `id`。两台车同一个 IP（或都走 NAT）会互相覆盖。
2. **`task` 有白名单**，只接受 7 种组合；发别的会被置空。
3. **`CV2` 不会被 `task` 限制**。容量截断时可能发 `AB-3` 但 `task` 是 `ABC`，核验时以 `CV2` 为准。
4. **JSON 必须是单行**。裁判用 `\n` 切分，多行会被当成多个坏包。

### 10.3 计分公式（软件口径，`mainwindow.cpp:1465-1508`）

```cpp
deliveryScore      = min(48, 单样本次数×8 + 两样本次数×12 + 三样本次数×18)
+ 干扰样本（一次 8 分）
+ 避障（8 分）
pickupBroadcast    = min(6,  取样播报次数×2)
board2Action       = min(12, 板二正确次数×4)
deliveryBroadcast  = min(6,  送样播报次数×2)
finalVerification  = min(12, 最终 MD5 核验次数×4)
                      ↑ 这里"次数"按圈算，4 分/圈 × 3 圈

总分 = min(100, deliveryScore + pickupBroadcast + board2Action
                + deliveryBroadcast + finalVerification)
      - 扣分

扣分 = 碰撞×2 + 部分出框×1 + 完全出框×3 + 堆积罚分
```

**得分优先级（从性价比看）**

| 项 | 满分 | 性价比 |
|---|---|---|
| 送样 48 分 | 48 | **最高**。一次送 3 个 = 18 分，跑 3 圈就 48 封顶 |
| MD5 核验 12 分 | 12 | **最容易拿**，但需要裁判配合操作（§10.6） |
| 板二 12 分 | 12 | 每次 4 分，3 次就满 |
| 取样播报 6 + 送样播报 6 | 12 | 每次 2 分，各 3 次就满 |
| 干扰/避障 | 16 | 看现场有没有 |

> **结论**：**跑得快不如跑得准**。3 圈各送 3 个样本 = 9 个样本，但 `max_samples=8` 封顶，所以是 3+3+2。只要每圈都对，48 分是稳的；再多跑也不加分。真正拉开差距的是 **MD5 12 分 + 播报 12 分 + 板二 12 分**（这 36 分全靠"细节不漏"）。

### 10.4 裁判界面怎么用（30 秒上手）

1. 双击 `smart.exe`（保持同目录的 DLL、`score_template.docx`、`generate_score_docx.ps1`、`Reports\` 都在）；
2. 顶部选择/输入队伍名称 → **开始比赛**（底部 3 分钟总计时开始走）；
3. 小车连上后，地图上会出现实时轨迹；右边能看到速度、任务、CV1/CV2；
4. 每当小车做对一个动作，裁判点对应的加分按钮（取样播报 / 板二 / 送样播报）；
5. **MD5 值核验**：点按钮 → 三圈各填"播报内容 + MD5" → 点"核验"（详见 §10.6）；
6. 一轮结束点 **结束比赛** → 导出 docx → 选"下一轮"或"下一队"。

### 10.6 MD5 核验（12 分，最容易丢的分）

**裁判端操作**
1. 主界面点 **【MD5值核验】**；
2. 窗口分**第一圈 / 第二圈 / 第三圈**三组；
3. 每组：左栏贴"播报内容"（一行一条），右栏贴对应 MD5（一行一个），**行号一一对应**；或只贴内容后点 **"自动计算全部 MD5"**；
4. 点该圈的 **"核验"** → 全绿 = 该圈 +4；也可以最后点 **"核验三组"**；
5. 三圈全绿 = **12 分**。

**五条格式铁律（错一条这圈就 0 分）**
1. 内容**原样复制**，行尾不要多空格（内容不做 trim）；
2. 一圈内**不要留空行**（中间空行会被判"内容为空"，整圈失败）；
3. 左右**行数必须相等**；
4. MD5 **32 位小写**（大写会自动转小写；带 `-` `:` 空格会被清除）；
5. 内容和 MD5 **必须成对替换**，不能沿用上一圈的。

**时机**：比赛中、暂停、"本轮刚结束但还没点【结束比赛】"时都能做。**一旦点了【结束比赛】并选完"下一轮/下一队"，本场的 MD5 记录会清零。**

**我们的 112 行对照表**（`D:\ISCC\md5_verify\MD5对照表.csv`）已经把 `L{圈}-{识别}-TO-{窗口}` × 4 圈 × 7 种识别 × 4 个窗口全算好了，现场直接查表粘贴即可，不用手算。

### 11.3 WSLg：两个必配环境变量

### 11.4 时钟：最容易被忽略的"玄学"来源

**症状**：RViz 空白但窗口正常、`Message Filter dropping message ... queue is full`、`tf` 拿不到对应时刻、AMCL 报 `timestamp earlier than all data`。

**根因**（真实案例）：
- 树莓派**无 RTC**，开机时间从 0 开始，chrony 一联网跳 51 天；
- Windows 的 `w32time` 服务没启动（`w32tm /query/status` 返回 `0x80070426`），主机比车慢 2.58 秒；
- 用 SSH 测时钟差时，**RTT 有 1~2.7 秒**，测出来的"偏差"虚高 4 倍（真实只差 0.2 s）。

**正确做法**
```bash
# 车端
timedatectl status | grep -E 'NTP|synchronized'   # 必须 yes
chronyc tracking                                   # System time / Stratum / Reference
date -u

# 主机（WSL）
date -u
chronyc tracking        # 26.04 里锁的是 PHC0，误差 0.17 µs

# 用 HTTP 时间做独立基准（别用本机时钟自证）
curl -sI https://www.baidu.com | grep -i '^date'
```

**三条经验**
1. **先校时，再起 Nav2**。顺序反了，AMCL 会丢光所有扫描。
2. **改完时钟必须重开 RViz**（旧实例缓冲已乱）。
3. **测时钟差要用 SSH 复用连接**（`ControlMaster`），否则 RTT 会骗你。

```powershell
iscc pre
#   会依次打点：起底盘/IMU/雷达 → 等 /odom → 相机 → restart nav → 等 IMU/Nav2 → 等图像
#   期望：最后一张 8 行服务表全是 active，并且 "ready in XXXs"
```

**`iscc pre` 卡住的三种典型**
| 卡在哪 | 说明 | 怎么办 |
|---|---|---|
| `waiting for /odom` | 底盘没起来 / 串口被占 | `iscc status`；`sudo systemctl restart eprobot-base`；`fuser /dev/EPRobot_base` |
| `waiting for Nav2 lifecycle` | 启动竞态 或 domain 不一致 | 先看 `iscc version` 的 domain 是不是 1；再 `iscc kill && iscc pre` |
| 最后图像那步一直打点 | 相机没出图 | `iscc status` 看 image 的发布/订阅数；`sudo systemctl restart openni2-camera mono8-relay` |

> **注意**：`iscc pre` 结束时 **Ctrl-C 只是停止看日志，车还在跑**。要停车用 `iscc stop` / `iscc kill`。

### 12.3 验收（6 项，全过才发车）

### 12.4 摆车与定初始位姿

1. **把车推到起点（`home` = 地图原点）**，车头朝 +x（yaw=0）。

2. **看 RViz 确认车的位置**（`iscc rviz2`）：

> **静止时 `/amcl_pose` 不更新是正常的**。别以为坏了——车一动就会更新。

## 13. 试错方法论（怎么不把自己坑死）

> 这一节比任何参数都值钱。过去两个月 90% 的时间浪费，不是"不会调参"，是"调了不知道有没有用、改坏了回不去"。

### 13.1 任何改动都走同一条流水线

```bash
# ① 备份（带用途和时间戳，方便日后认）
cp -p <file> <file>.bak_<用途>_<YYYYMMDD_HHMMSS>

# ② 改

# ③ 语法/静态检查（Python 2 项目尤其重要）
python2 -c "import py_compile; py_compile.compile('<file>', doraise=True); print('PY2 OK')"

# ④ 重启对应服务/launch，实车验证（不是"起来了"就算）

# ⑤ 验证通过 → 立刻提交（只 add 本次文件）
git -C ~/robot_ws/src status --short
git -C ~/robot_ws/src add <只列本次改的文件>
git -C ~/robot_ws/src commit -m "tune(pharmacy): <what and why>"
git -C ~/robot_ws/src push

# ⑥ 确认工作区只剩预期的历史脏文件
git -C ~/robot_ws/src status --short
```

**绝对禁止**
- `git add -A` / `git add .` / `git commit -a`（仓库有 100+ 历史脏文件，一把梭全进去）
- 只改不提交（换机器/回滚就丢）
- 提交了但不 push（"我改好了"其实只在车上的磁盘里）

### 13.2 一次只改一个变量

反例（真实发生过）：同时改 `consider_footprint: true` + `resolution: 0.05→0.02`，Nav2 起不来，**无法归因**，只能整文件回滚。

正例：先只改 `resolution`，验证；再只改 `consider_footprint`，验证。

### 13.3 判据必须可量化

| 你要判断 | 不要用 | 要用 |
|---|---|---|
| 识别行不行 | "看起来能认" | 码宽像素数（≥55 可解、≥80 稳）；`qr_accepted` 次数 |
| 限速有没有生效 | "好像慢了" | 距离扫描：3.0/1.2/0.75/0.55/0.25 m 各读 `/speed_limit` |
| 到点准不准 | "差不多到了" | `navigation.jsonl` 里 `delivered` 前后的距离；RViz 里看车是否在框内 |
| 定位飘不飘 | "感觉有点飘" | `map→odom` 的最大跳变（>0.3 m 就是问题） |
| CPU 高不高 | "风扇响" | `ps -eo pcpu,comm --sort=-pcpu \| head`；`load average` |
| 语音有没有播 | "好像有声" | `speech_finished` 的 `status == DONE` |

### 13.4 回滚要能在 10 秒内完成

- **单文件回滚**：`cp -p <file>.bak_<用途>_<TS> <file>` + 重启服务
- **整文件回滚**：`git checkout <commit> -- <path>`
- **整仓回滚**：`git revert <commit>`（不要 `reset --hard`，会丢别人的提交）

**回滚后必须重启**。很多"改了没生效"其实是文件改了、进程还在用旧代码。

### 13.5 git 纪律（队规，写进 AGENTS.md）

| 规则 | 原因 |
|---|---|
| 提交信息用英文 + Conventional Commits（`feat/fix/tune/refactor/docs`） | 665 次提交的历史都是这个风格，好检索 |
| 一次提交只做一件事 | 出问题好 revert |
| 改前 `git pull --rebase` | 多机协作，避免在旧树上改 |
| **任务运行中不要 `git pull`** | 正在跑的 `roslaunch` 会读到被替换的文件 |
| 未跟踪的关键文件改了要 `git add` | `robot_localization.launch`、`base_control.py`、`audio/*.wav` 历史上都是 `??` 状态，不 add 等于没改 |

### 13.6 什么时候该停手

出现下面任一情况，**立刻 `iscc stop` / `stop_pharmacy_stack.sh`，先记录再动手**：

- 车开始"抽搐"（位姿来回跳、方向乱打）；
- 连续两次同样的失败（说明不是偶然）；
- 改了参数后**比之前更差**（先回滚，再想）；
- 电池 < 11 V；
- 场地里有人/有杂物；
- 你已经 20 分钟没有可量化的进展。

### 13.7 时间盒：给每次尝试定一个上限

| 尝试类型 | 时间盒 | 到点怎么办 |
|---|---|---|
| 改一个参数 | 15 分钟 | 没效果就回滚，记录"无效" |
| 查一个"玄学"问题 | 30 分钟 | 没定位到就绕过（换后端/换方案），记进"未解问题" |
| 装环境/装包 | 1 小时 | 换镜像源、换路径，别死磕 |
| 跑一次完整流程 | 单圈 90 秒 | 超时就是有问题 |

### 13.8 每次实验都要留"可复现的三件套"

1. **改了什么**（文件 + diff 摘要）
2. **期望什么**（可量化）
3. **实测什么**（数据/日志片段/截图）

写在一个 `实验记录.md` 里，按日期倒序。三个月后你会感谢自己。

## 14. 踩坑总表（按现象查）

> 用法：出问题先在这里找现象。**"一步验证"那一列是让你 10 秒内分清方向，不要跳过。**

### 14.1 连不上 / 起不来

| 现象 | 真因 | 一步验证 | 修复 |
|---|---|---|---|
| `ssh: No route to host` | 车离线 / WiFi 掉 / IP 改了 | `ping <ip>`；`arp -a` | 等车重连；确认热点；`ip route` |
| `Permission denied (publickey)` | 换了车/换了系统，key 不对 | `ssh -v` | 用密码登；或重配 `authorized_keys` |
| `iscc` 连到错误的车 | `~/.bashrc` 覆盖了 `ROBOT_IP` | `echo $ROBOT_IP`；`iscc version` | 删掉 `export ROBOT_IP`，只留配置文件 |
| `iscc start` 报 `eprobot-nav is not active` | 没 pre / nav 挂了 | `iscc status` | `iscc pre` |
| `roslaunch` 直接报 `RLException: env ROBOT_TYPE` | 没导出环境变量 | `echo $ROBOT_TYPE` | `export ROBOT_TYPE=EPRobotV2.3` |
| Nav2 卡在 `waiting for Nav2 lifecycle` | ①domain 不一致 ②启动竞态 ③`/is_path_valid` 1 s 超时 | `iscc version` 的 domain；`journalctl -u eprobot-nav \| tail -50` | 统一 domain；`iscc kill && iscc pre`；等 180 s 别急着重启 |
| `Failed to bring up all requested nodes` | costmap 激活时 TF 未就绪 | journal 里往前找 `Timed out waiting for transform` | 先保证 `/odom` 有帧再 restart nav |
| 服务 `activating (auto-restart)` 反复重启 | 依赖缺失/设备被占 | `journalctl -u <unit> -n 50` | 修依赖；`pkill` 占设备的进程 |

### 14.2 "有话题但没数据"

| 现象 | 真因 | 一步验证 | 修复 |
|---|---|---|---|
| `ros2 topic hz` 一直是 0 | **QoS 不兼容** | `ros2 topic info -v <topic>` 看 Publisher/Subscription 的 Reliability | 加 `--qos-reliability best_effort`；或改订阅端 |
| 节点都在，`ros2 node list` 空 | **domain 不一致** | 车 `systemctl show eprobot-base -p Environment` vs 主机 `echo $ROS_DOMAIN_ID` | 统一为 1 |
| 突然全部收不到 | **Fast DDS SHM 泄漏** | `ls /dev/shm \| grep -c fastdds`（正常个位数） | `iscc kill`（先 pkill 再 stop 再清） |
| `Failed init_port fastdds_port70xx` | 同上（端口耗尽） | 同上 | 同上 + 给 unit 加 `FASTDDS_BUILTIN_TRANSPORTS=UDPv4` |
| 跨机 `/scan` 能到、`/scan_viz` 不能到 | DDS 端点匹配不稳定，**不是丢包** | 同尺寸话题做对照实验 | 别死磕；远程 RViz 只作辅助 |
| `/scan` 有话题、Publisher count = 0 | 雷达驱动进程活着但没出数据 | `ros2 topic info /scan`；`journalctl -u lslidar` | `sudo systemctl restart lslidar` |
| `/amcl_pose` 静止时没数据 | **正常**（AMCL 只在移动/更新阈值时发） | 推一下车 | 不用修 |

### 14.3 相机 / 识别

| 现象 | 真因 | 一步验证 | 修复 |
|---|---|---|---|
| `/dev/video0` 不存在 | **Astra S 没有 UVC** | `lsusb`（只有厂商私有类） | 走 OpenNI2，别用 `v4l2_camera` |
| `Image buffer is corrupt. Size is 371790 (!= 921600)` | 加了无效的 `color_mode`；或 USB2.0 丢包 | 看日志频率 | **删掉 `color_mode` 参数**；<1% 的偶发可接受 |
| 相机起不来，`failed to claim usb interface: BUSY` | 厂商进程 `orbbec_as` 占着 | `ps \| grep orbbec` | `pkill -f orbbec_as`；必要时 USB unbind/bind |
| `ros2 param set` 找不到相机节点 | **DDS SHM 按用户隔离**（root 看不见 keyuan22 的节点） | 用 `keyuan22` 身份跑一次 | 服务用 `User=keyuan22` + `HOME=/home/keyuan22` |
| 有图但识别不出 | ①编码不是 mono8 ②码太小 ③过曝 | `ros2 topic echo --once` 看 `encoding`；抓帧量码宽 | 加 relay 转 mono8；车再近 10 cm；曝光 40~100 |
| 日志里连 `QR scan:` 都没有 | 图像订阅都没建立/编码转换直接抛异常 | 检查 `/detection_control` 是否为 true | 看 F1 是否卡在上一步 |
| `candidates=1~2 hits=0/3` | 码太小（<55 px）或太糊 | 抓帧量像素 | 近一点/调曝光/调角度 |
| 板二永远说"等 8 秒" | 用了模板后端（只会输出 BUSY_8）。**ROS 2 车默认不是模板**，若这句成立说明有人把 `board2_backend` 改成了 `fixed`/`template` | 车端 `systemctl cat eprobot-pharmacy` 看 ExecStart；`ros2 node list \| grep board2` | 去掉覆盖参数，或显式 `board2_backend:=rapidocr` |
| 板二频繁返回 FREE 但现场是 BUSY | `template` 后端的 `fallback_state=FREE` 在编造 | 看 `/pharmacy/board2_timing` 的 `reason` | 换 `fixed`（强拒识）或 `rapidocr` |

### 14.4 语音

| 现象 | 真因 | 一步验证 | 修复 |
|---|---|---|---|
| 完全没声音 | `keyuan22` 不在 `audio` 组 | `aplay -l`（报 no soundcards 就是权限） | `sudo usermod -aG audio keyuan22` + 重启服务 |
| `speech_finished status=MISSING` | 文字与 manifest 的 `text` 不严格相等 | 打印实际 text 与清单比对 | 改文案或补 wav |
| `status=FAILED` 且只有 Python 版 | `paplay` 失败（headless 没有 PulseAudio） | `echo $XDG_RUNTIME_DIR` | 改用 `aplay plughw:0,0`（ROS 2 车已是） |
| `status=MOTION_DETECTED` | 说话时车动了 | 看该时刻 `/odom` | 检查 `settle()` 是否超时；别在坡上播报 |
| `status=TIMEOUT` | 播放卡住 15 s | `aplay` 手工试同一文件 | 换设备/换文件；查 SD 卡是否慢 |
| 喇叭没声但以为坏了 | 喇叭是**板载 3.5 mm**，不是 USB 设备 | `cat /proc/asound/cards` | 查 3.5 mm 线；USB 只接 IMU/雷达/相机 |

### 14.5 导航 / 定位

| 现象 | 真因 | 一步验证 | 修复 |
|---|---|---|---|
| 车"抽风"、位姿来回跳 | `/odom` 有 **2 个发布者**（多车同域） | `rostopic info /odom` / `ros2 topic info /odom -v` | 给每台车分 `ROS_DOMAIN_ID` |
| 激光图整体旋转 | 雷达整帧用第一束时间戳，100 ms 运动畸变 | 看 `scan_time` / `time_increment` | 降速转弯；或做去畸变 |
| `Failed to make progress` | ①电池低压 ②轮子打滑 ③目标不可达 | 先看电压 | 充电；换点；放宽进度判据 |
| 到不了框 | 目标点离墙 < 0.18 m（半对角） | 地图上量距离 | 挪点或改朝向 |
| **B 点蹭墙** | 45° 收尾需要"边走边转"，右甩 ~0.14 m，余量仅 0.28 m | RViz 看轨迹 | 降速（已做）；根治：C 点 yaw 改 105° / B 点 yaw 改 90°（**均未实施**） |
| A 点偶发倒车/呆退 | A 余量 0.244 m < 半对角 0.29 m | 看 `mission.jsonl` 的 `ac_transit` 段 | 放宽进度判定（已做）；或挪 A |
| 定位飘到别处 | 初始位姿错 / Cartographer 没放在建图起点 | RViz 看车与墙是否重合 | 重新给 `2D Pose Estimate`；重开 |
| 停车后 AMCL 不更新 | 正常行为 | 推一下车 | — |

### 14.6 时间 / 时钟

| 现象 | 真因 | 一步验证 | 修复 |
|---|---|---|---|
| AMCL `timestamp earlier than all data` | 车时钟跳了几十天 | `date`；`chronyc tracking` | 先校时再起 nav |
| RViz 空白但窗口正常 | 主机/车时钟差 >0.5 s | 三方对比（车 / 主机 / 百度 HTTP Date） | 校主机时钟；重开 RViz |
| `Message Filter dropping ... queue is full` | 同上（TF 时间戳对不上） | 同上 | 同上 |
| 测出来"车快 3 秒"，实际只差 0.2 s | SSH 建连 RTT 1~2.7 s | 用 `ControlMaster` 复用连接重测 | 别信单次测量 |

### 14.7 流程 / 人为

| 现象 | 真因 | 修复 |
|---|---|---|
| `iscc pre` 后车不动 | ROS 2 的 `pre` 只热车 | `iscc start` |
| `.24` 上敲 `iscc pre` 结果车冲出去 | ROS 1 的 `pre` 是"一条龙" | **先清场**；或改用 `start_nav_camera_detect.sh` |
| Ctrl-C 后车还在跑 | 两边都是"只停止看日志" | `iscc stop` / `stop_pharmacy_stack.sh` |
| `iscc pre` 闪退无输出 | bash `set -e` + `grep -c` 匹配 0 返回 1 | 加 `\|\| true`（已修） |
| 改了点位没生效 | 改的文件不是实际加载的那份 | 打印实际参数：`rosparam get` / `ros2 param get` |
| 改了 config 但行为没变 | 服务没重启 / 进程还在用旧文件 | 重启对应 unit |

### 14.8 裁判

| 现象 | 真因 | 一步验证 | 修复 |
|---|---|---|---|
| 裁判界面没数据 | ①软件没开 ②IP 不对 ③`judge_tcp` 没起 | `netstat -ano \| findstr 8888`；车上 `nc -zv <ip> 8888` | 逐项修（§10.5） |

### 16.1 术语

| 术语 | 解释 |
|---|---|
| **节点 / node** | 一个 ROS 进程 |
| **话题 / topic** | 广播频道 |
| **消息 / message** | 话题里的数据结构 |
| **TF** | 坐标变换树（带时间戳） |
| **launch** | 批量启动脚本 |
| **AMCL** | 自适应蒙特卡洛定位（粒子滤波 + 地图匹配） |
| **Cartographer** | Google 的 SLAM/定位库，纯定位用 `.pbstream` |
| **EKF** | 扩展卡尔曼滤波（这里用于融合 odom + IMU） |
| **move_base** | ROS 1 的导航框架（全局规划 + 局部规划 + 恢复） |
| **Nav2** | ROS 2 的导航框架（lifecycle 节点 + BT 行为树） |
| **TEB** | 时间弹性带局部规划器（ROS 1 用） |
| **MPPI** | 模型预测路径积分控制器（ROS 2 用） |
| **Smac Hybrid** | 混合 A*/Reeds-Shepp 全局规划器 |
| **costmap** | 代价地图（障碍 + 膨胀） |
| **footprint** | 车体多边形（用于碰撞检测） |
| **inflation_radius** | 障碍膨胀半径（决定车能贴墙多近） |
| **DDS** | ROS 2 的通信中间件（Fast DDS） |
| **QoS** | 通信质量策略（Reliability / Durability） |
| **domain id** | DDS 域号，不同域互不可见 |
| **SHM** | 共享内存（`/dev/shm/fastdds_*`） |
| **mono8 / rgb8 / bgr8** | 图像编码：单通道灰度 / RGB / BGR |
| **CV1 / CV2** | 裁判协议字段：板二结果 / 板一结果 |
| **`ac_transit`** | ROS 2 车 C→A 之间的中转点（删了会退化成 C→A） |
| **`P` 点** | ROS 1 车 C→A 之间的中转点（配合倒车进 A） |
| **`qr_reposition`** | 识别失败后的"退一点再进"点 |

## 18. 网络：换 IP、切换"自发热点 / 连热点"

### 18.1 两种工作模式，先分清

| 模式 | 谁发信号 | 车怎么配 | 优点 | 缺点 |
|---|---|---|---|---|
| **STA**（客户端 / 连热点） | 外部热点（手机） | `netplan` 写死 SSID+密码+静态 IP | 多台车可同网、能上外网、能跑 NTP | 依赖手机热点；SSID 重名会连错 |
| **AP**（自发热点） | **车自己** | `hostapd`+`dnsmasq`，或 NetworkManager hotspot | 不依赖外部、开机即用 | 一台电脑只能连一台车；车无外网 → **无 NTP** |

**两辆车的现状（2026-11-13 实测 + 你提供的信息）**

| 车 | 模式 | SSID / 密码 | 车 IP | 实测依据 |
|---|---|---|---|---|
| `.22`（EPRobot2） | **STA** | 连 `OnePlusAce5` / `<REDACTED>` | `10.211.121.22/24`，网关 `.1` | `netplan` 两个文件里都写着这个 SSID；`nmcli` 空、`hostapd`/`dnsmasq` 均 `inactive`；`wlan0` 上有静态地址 |
| `.21`（EPRobot1，卡在 `.22` 上） | **AP** | 自发热点 `yaofang` / `<REDACTED>` | `10.211.121.21` | 用户提供；⚠️ 车现在无卡，未能实机复核 |

> **一个反直觉的现象**：`.22` 同时存在 `wlan0 10.211.121.22` 和 **`tunx 10.7.7.2`**（实测 `ip route` 里有 `10.7.0.0/16 via 10.7.7.1`、`192.168.100.0/24 via 10.7.7.1`）。`tunx` 是 VPN 隧道（ZeroTier 一类），`iscc` 包里那个"默认 `ROBOT_IP=10.7.7.2`"就是从这来的。**看到日志里出现 `10.7.7.2` 不要慌**，那是同一台车的另一个身份。详见 §18.5。

### 18.2 换 IP：这台车上正确且安全的做法

#### 第 0 步：先看现在是怎么配的（别猜）

```bash
ls /etc/netplan/
# 实测输出：01-wlan0.yaml   50-cloud-init.yaml
```

**这台车有两个文件同时配 `wlan0`**，这是最大的坑：

| 文件 | 来源 | 实测内容 |
|---|---|---|
| `01-wlan0.yaml` | 人写的（带注释 `# EPRobot Pi 4 Wi-Fi client mode with static address.`） | renderer `networkd`；`10.211.121.22/24`；default via `10.211.121.1`；DNS `114.114.114.114` / `223.5.5.5`；AP `OnePlusAce5` |
| `50-cloud-init.yaml` | **cloud-init 自动生成** | 同样的 IP / 网关 / DNS / AP，只是 YAML 格式不同（`auth: key-management: psk`） |

> **netplan 按文件名字典序合并，后读的覆盖先读的**。`01-` 在前、`50-` 在后 → **同一组键最终以 `50-cloud-init.yaml` 为准**。
> 所以**只改 `01-wlan0.yaml` 很可能白改**。
>
> **别猜，直接看"最终生效值"**（推荐养成这个习惯）：
> ```bash
> sudo netplan get            # 打印合并后的完整配置（netplan ≥0.103 支持）
> sudo netplan --debug apply  # 看它读了哪些文件、合并顺序
> ```

#### 第 1 步：改（推荐两条文件一起改）

```bash
# 备份（永远先备份）
sudo cp -p /etc/netplan/01-wlan0.yaml /etc/netplan/01-wlan0.yaml.bak_ip_$(date +%Y%m%d_%H%M%S)
sudo cp -p /etc/netplan/50-cloud-init.yaml /etc/netplan/50-cloud-init.yaml.bak_ip_$(date +%Y%m%d_%H%M%S)

# 方案 A（推荐）：只留一份权威配置，把 cloud-init 那份停掉
sudo rm /etc/netplan/50-cloud-init.yaml
#   并禁止 cloud-init 再生成网络配置（否则重启又回来）：
sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg >/dev/null <<'EOF'
network: {config: disabled}
EOF

# 然后只改 01-wlan0.yaml
sudo nano /etc/netplan/01-wlan0.yaml
```

`01-wlan0.yaml` 的实测原文（照这个结构改，别自己发明缩进）：

```yaml
network:
  version: 2
  renderer: networkd
  wifis:
    wlan0:
      dhcp4: false
      dhcp6: false
      addresses:
        - 10.211.121.22/24          # ← 改成你要的 IP
      routes:
        - to: default
          via: 10.211.121.1         # ← 网关，必须和热点同网段
      nameservers:
        addresses:
          - 114.114.114.114
          - 223.5.5.5
      access-points:
        "OnePlusAce5":              # ← 热点名，注意引号
          password: "<REDACTED>"      # ← 热点密码
```

**缩进是 2 空格、不能用 Tab**；`addresses` 必须是 CIDR（带 `/24`）；`routes` 的 `to: default` 不能写成 `0.0.0.0/0`（能写但容易错）。

#### 第 2 步：应用 ——**远程改网络必须用 `netplan try`**

```bash
sudo netplan try        # 应用但等 60 秒；不按回车 = 自动回滚
sudo netplan apply      # 确认没问题后，或直接一次性应用
```

> **`netplan try` 是远程改网络的救命开关**：它先把配置应用上去，然后倒计时 60 秒等你按回车确认；超时或按 Ctrl-C 就**自动恢复旧配置**。如果你是把车 IP 改成了电脑不在的网段，`try` 会让你在 60 秒后自动"活过来"。
> 用 `netplan apply` 改错了，SSH 当场断，车还留在错误 IP 上——只能靠网线/键鼠/插显示器救。

#### 第 3 步：三条验证（缺一条都不算成功）

```bash
ip -4 addr show wlan0          # 必须是新 IP/24
ip route                       # default via <网关> dev wlan0 —— 必须指向热点网关
ping -c2 10.211.121.1          # 网关通
ping -c2 223.5.5.5             # 外网通（NTP 依赖它，见 §11.4）
```

**网关配错的历史教训**：曾把网关写成 `10.211.121.121`，结果**车能连上、但无外网、无 NTP**，然后所有"时间不对 → RViz 空白 → AMCL 丢扫描"的故障都从这个错配长出来。`ip route` 里 `default` 那一行必须和热点网关一致（手机热点一般是 `.1`）。

#### 第 4 步：改完 IP 必须同步的 6 个地方（漏一个就连不上）

| # | 位置 | 怎么改 |
|---|---|---|
| 1 | WSL 里的 `iscc` 配置 | `~/.config/iscc/iscc.conf` 的 `ROBOT_IP=` |
| 2 | WSL 的 SSH 别名 | `~/.ssh/config` 里 `Host robot` 的 `HostName` |
| 3 | `~/.bashrc` 里的导出 | 有 `export ROBOT_IP=` 就要改（**它会覆盖配置文件**，历史踩过） |
| 4 | 车端裁判地址 | `pharmacy.yaml` 的 `judge_tcp.host`（那是裁判机 IP，不是车 IP，别搞混） |
| 5 | 写死 IP 的脚本 | `grep -rn "10\.211\.121\." ~/robot_ws/src ~/bin /usr/local/bin 2>/dev/null` |
| 6 | 另一台车 | **别撞 IP**（`.21` / `.22` / `.24` 各有归属，见 §19.1） |

改完 `iscc version` 必须看到新的 `robot:` 行（§2.2 的"认车四问"）。

#### 第 5 步：回滚

```bash
# 有备份
sudo cp -p /etc/netplan/01-wlan0.yaml.bak_ip_<时间戳> /etc/netplan/01-wlan0.yaml
sudo netplan apply
# 没备份（或改乱了）
sudo netplan try       # 会加载磁盘上的配置，若也错就等它回滚
```

**最坏情况**：IP 改到够不着的网段。此时**只能物理接触**——插网线（如果网卡支持）、接 HDMI+键鼠、或把 SD 卡拔下来在另一台机器上改（⚠️ 这需要读卡器 + Linux，见 §19.4）。

### 18.3 切换"连热点" ↔ "自发热点"

#### 从 AP 切到 STA（`.21` 的风格 → `.22` 的风格）

```bash
# 1) 先确认现在是谁在发信号
systemctl is-active hostapd dnsmasq      # AP 模式这两个通常 active
systemctl is-active NetworkManager systemd-networkd wpa_supplicant
#   .22 实测：NetworkManager=inactive, systemd-networkd=active, wpa_supplicant=active
#             hostapd=inactive, dnsmasq=inactive  → 纯 STA，没有 AP 能力

# 2) 停掉 AP 相关服务
sudo systemctl disable --now hostapd dnsmasq

# 3) 把 wlan0 改成 STA 配置（照 §18.2 的 yaml，access-points 写目标热点）
sudo netplan try
```

**注意**：`hostapd` 和 `wpa_supplicant` **抢同一个 `wlan0`**，不能同时开；切模式必须停掉另一个，否则 `netplan apply` 会报 `wlan0: interface is busy` 或干脆不生效。

#### 从 STA 切到 AP（`.22` → 自己发 `yaofang`）

有三条路，**按"改动面从小到大"排序**：

**路线 ①：查厂商是不是已经写好了脚本**（最省事，先试这条）

```bash
grep -rl "yaofang" /etc /usr/local/bin /usr/local/sbin /opt 2>/dev/null | head
# 本车没查到（因为它是 STA 配置），但 .21 的卡里很可能有
```

如果 `.21` 卡里能找到 `/usr/local/bin/*ap*` 或 `/etc/hostapd/*.conf`，**直接抄它的做法**比自己发明可靠（§19.5 会说怎么从卡里找）。

**路线 ②：NetworkManager（一条命令，但会抢管理权）**

```bash
# 注意：本车 NetworkManager 是 inactive，启用它会和 systemd-networkd 抢 wlan0
sudo systemctl enable --now NetworkManager
sudo nmcli device wifi hotspot ifname wlan0 ssid yaofang password '<REDACTED>'
# 默认会给 wlan0 一个 10.42.0.1/24 的地址，不是 10.211.121.21
sudo nmcli con mod Hotspot ipv4.addresses 10.211.121.21/24 ipv4.method manual
sudo nmcli con up Hotspot
```

代价：`systemd-networkd` 管的 `netplan` 配置会失效；下次开机行为不确定。**不建议在这台车上用**，除非你愿意把网络管理整体切到 NetworkManager。

**路线 ③：hostapd + dnsmasq（Pi 上的经典做法，最可控）**

```bash
sudo apt install -y hostapd dnsmasq
sudo systemctl unmask hostapd

# /etc/hostapd/hostapd.conf
interface=wlan0
driver=nl80211
ssid=yaofang
hw_mode=g
channel=6
wpa=2
wpa_passphrase=<REDACTED>
wpa_key_mgmt=WPA-PSK

# /etc/dnsmasq.d/wlan0.conf  （给连上来的电脑发 IP）
interface=wlan0
dhcp-range=10.211.121.100,10.211.121.200,12h

# netplan 里 wlan0 改成静态、不写 access-points
sudo netplan try

sudo systemctl enable --now hostapd dnsmasq
```

**⚠️ 三个硬约束**
1. **网卡要支持 AP 模式**：`iw list | grep -A8 "Supported interface modes"` 里必须有 `AP`。没有就是没有，改不了。
2. **2.4G / 5G**：`hw_mode=g` 是 2.4G，兼容性最好；`hw_mode=a` 需要网卡支持且要配 `channel`。
3. **DHCP 池不能和静态 IP 撞**：车是 `.21`，池就开在 `.100~.200`。

#### 切换时的"自锁"风险（必须防）

改网络/切模式时，**你正通过这个网络连着车**。一旦配置生效、连接断了，你就再也连不回去。三个标准防护：

```bash
# 防护 1：定时回滚（最实用）——180 秒后自动恢复备份
sudo bash -c 'nohup sh -c "sleep 180; cp -p /etc/netplan/01-wlan0.yaml.bak_ip_xxx /etc/netplan/01-wlan0.yaml; netplan apply" >/tmp/netrollback.log 2>&1 &'

# 防护 2：用 netplan try（它自带 60 秒回滚）
sudo netplan try

# 防护 3：插网线/接屏幕，让"物理接触"成为保底
```

**验证切成功了**：手机能搜到 `yaofang` → 连上（密码 `<REDACTED>`）→ `ping 10.211.121.21` 通 → 电脑拿到 `10.211.121.x` 的地址。

> **两车同时开 AP 会重名**：都叫 `yaofang` 时，电脑会随机连上一台，表现为"命令时好时坏"。现场**只开一台 AP**，或把 SSID 改成 `yaofang-21` / `yaofang-22`。

### 18.4 多车同网必须分 `ROS_DOMAIN_ID`

| 车 | domain | 依据 |
|---|---|---|
| `.22` | **1** | 所有 unit 的 `Environment=ROS_DOMAIN_ID=1`；`iscc version` 显示 `domain: 1` |
| `.21` | ⚠️ 未确认 | 卡拔了查不到；插回后看 `systemctl cat eprobot-base \| grep DOMAIN` |

**同域的后果**（真实踩过）：两台车都把 `/odom`、`/scan`、`/tf` 发到同一个 DDS 域 → 你在 `.22` 上会看到**两个 `/odom` 发布者**，位姿在两个值之间来回跳，RViz 里表现为"雷达图整体旋转/漂移"。**这不是雷达坏，是串车。**

```bash
# 判断有没有串
ros2 topic info /odom -v | grep -E "Publisher count|Node name"
# Publisher count 应该是 1；2 就是串了
```

**分域原则**：一车一域（`.21`=2、`.22`=1 之类），并在**所有** unit + `iscc.conf` + 主机侧环境变量里保持一致（§6.7 的"domain 不一致"排障）。

### 18.5 隐藏网卡 `tunx`：同一台车的第二个身份

实测 `.22` 上有：

```
4: tunx    inet 10.7.7.2/24
default via 10.211.121.1 dev wlan0 proto static
10.7.0.0/16      via 10.7.7.1 dev tunx metric 200
192.168.100.0/24 via 10.7.7.1 dev tunx metric 200
```

**它是什么**：VPN 隧道（ZeroTier/OpenVPN 一类）的虚拟网卡。`tunx` 通的时候，这台车同时是 `10.211.121.22` 和 `10.7.7.2`。

**三个影响**
1. `iscc` 安装包的默认 `ROBOT_IP=10.7.7.2` 就是从这来的——**别以为那是"队友的电脑"**（历史文档里这么写过）。
2. `ip route` 里有 `metric 200` 的 VPN 路由，一般不会抢默认路由；但如果 VPN 那头也发了默认路由，**裁判流量可能被带走**。
3. 日志里出现 `10.7.7.2` 的连接、`ros2 node list` 里出现异地节点，先想到它。

**处理**（比赛现场建议）

```bash
ip route | grep tunx           # 先看有没有
sudo ip link set tunx down     # 临时关（重启会回来）
systemctl list-units | grep -i -E "zerotier|tailscale|openvpn|wg"   # 找是谁起的
```

> ⚠️ 关掉之前确认**没有别人正通过 VPN 连这台车**（远程支持/队友调试）。关掉就断了。

| 相机脚本 | `/mnt/sd21/usr/local/bin/openni2-camera` |
| 地图 | `/mnt/sd21/home/ubuntu/maps/` |
| 家目录 | `/mnt/sd21/home/ubuntu/` |
| ROS 安装 | `/mnt/sd21/opt/ros/lyrical/` |

### 19.2 一个必须先说清的混乱：**两台机器都叫 `EPRobot1`**

| 机器 | 主机名 | 账号 | ROS | 出处 |
|---|---|---|---|---|
| `.24`（历史 ROS 1 车） | **`EPRobot1`** | `EPRobot` / `<REDACTED>` | Melodic | `AGENTS.md` §2 |
| `.21`（现在的初代 ROS 2 车） | **`EPRobot1`** | `ubuntu` / `<REDACTED>` | Lyrical | 你给的表 |

**所以 `hostname` 不能用来认车。** 认车只用：**IP + 账号 + ROS 版本**（§2.2）。

### 19.3 为什么 `.21` 现在是"关机/无系统"状态

因为**它的系统卡被拔出来插到了 `.22` 的 USB 读卡器上**。树莓派没有板载存储，卡一走就是"没有系统"，自然开不了机、也不会发 `yaofang` 热点。

实测 `.22` 的块设备（`lsblk`）：

```
NAME          SIZE  FSTYPE  LABEL        MOUNTPOINT
sda          59.5G
├─sda1        512M  vfat    system-boot        ← 未挂载
└─sda2         59G  ext4    writable           ← 未挂载（.21 的根文件系统）
mmcblk0     116.5G                              ← .22 自己的卡
├─mmcblk0p1   512M  vfat    system-boot  /boot/firmware
└─mmcblk0p2   116G  ext4    writable     /
```

**两张卡的结构完全一样**（都是 `system-boot` + `writable`，Raspberry Pi OS 的标准布局），所以**看错设备名就会写坏系统**。判定方法只有一个：**看挂载点**——`/` 挂着的那个是 `.22` 自己的（`mmcblk0p2`），`sda*` 是外来的。

### 19.4 读卡：完整步骤（只读！）

```bash

# 1) 确认卡在、确认设备名（关键：sda 可能是 sdb，别写死）

#   要看到 sda1 vfat system-boot + sda2 ext4 writable，且都没有挂载点

# 2) 建挂载点并【只读】挂载
sudo mkdir -p /mnt/sd21
sudo mount -o ro /dev/sda2 /mnt/sd21

# 3) 先确认身份（防止读错卡）
sudo cat /mnt/sd21/etc/hostname
#   期望：EPRobot1

# 4) 找代码 / 看配置
sudo ls /mnt/sd21/opt/eprobot_ws/src/
sudo find /mnt/sd21/home/ubuntu -maxdepth 2 -type d | head -30
sudo cat /mnt/sd21/home/ubuntu/<REDACTED>_navigation/scripts/goal_speed_limit.py
sudo cat /mnt/sd21/opt/eprobot_ws/install/pharmacy_pkg/share/pharmacy_pkg/config/mission_waypoints.yaml

# 5) 拷出来（比如拷到 .22 的 /tmp，再用 scp 拉走）
sudo cp -a /mnt/sd21/opt/eprobot_ws/install/pharmacy_pkg/share/pharmacy_pkg/config /tmp/sd21_config
```

### 19.5 卡里最值得捞的三样东西

1. **`.21` 的导航/任务配置全量**：`nav2_params.yaml`、`mission_waypoints.yaml`、`goal_speed_limit.py`。**这是两台车"同款但不同标定"的差异来源**，比任何文档都准。
2. **`.21` 是怎么发 AP 的**：`/mnt/sd21/etc/systemd/system/` 下找 `hostapd` / `dnsmasq` / `*hotspot*`；`/mnt/sd21/etc/hostapd/hostapd.conf`；`/mnt/sd21/boot/firmware/firstrun.sh` 里的 SSID/密码。**这就回答了 §18.3 的"路线①"**。
3. **`/opt/eprobot_ws/src/` 里到底有没有 `pharmacy_pkg`**：如果有，那就是 `.21` 的**源码**（`.22` 上没有）。这条能直接解决 §17.3 第 8 项"任务逻辑不可改"。

### 19.6 六条纪律（写坏了修不回来）

| 纪律 | 为什么 |
|---|---|
| **只用 `-o ro`** | 写坏 ext4 → `.21` 开不了机 |
| **读完立刻 `umount`** | 不卸载就拔读卡器 = 脏文件系统，开机要 `fsck` 甚至起不来 |
| **动手前 `lsblk` 确认设备名** | `sda` 可能变 `sdb`；`mmcblk0p2` 是 `.22` 自己的系统盘，**碰它等于自杀** |
| **不在挂载点上跑 `git` / `apt` / 编译器** | 会写 `.git/index`、缓存、锁文件 |
| **不 `fsck`、不 `resize2fs`、不 `chmod -R`** | 都会写元数据 |
| **拔卡前先在 `.22` 上 `umount`，再断电** | 带电拔 = 最危险的场景 |

> **我本轮的取舍**：按"两辆车代码不动"的原则，**没有执行挂载**。上面的命令是按你给的流程 + `lsblk` 实测写的，可以照着做；要我现在挂上去读 `.21` 的配置，说一声我再动手（仍用只读）。

## 20. 板二识别怎么"训练"

### 20.1 先明确"训练"在这里指什么

板二不是深度学习任务，**没有"训模型"这一步**。实际做的是：

```
采数据 → 选模板 / 选预处理 → 定阈值 → 批量回放验证 → 现场验收
```

三条技术路线，前两条是"模板匹配"（其实是**选模板 + 调阈值**），第三条才是 OCR（**调预处理 + 调后处理规则**）。

### 20.2 三条路线，先选对

| 路线 | 你实际在调什么 | 能识别 | 单次耗时（Pi 4B 实测） | 适合 |
|---|---|---|---|---|
| **C++ `fixed`**（`pharmacy_board2_fast_node`） | 2 张整牌模板 + 8 个阈值 | **只有 FREE / BUSY_8** | **40 ms** | 只要"空/忙"、要求快、能接受"忙就等 8 秒" |
| **Python `template`**（`board2_template_node.py`） | N 张 IDLE/BUSY 模板 + 3 个阈值 | **只有 FREE / BUSY_8** | 文档称 ~28 ms（⚠️ 未复测） | 想快速换模板、不介意 Python 开销 |
| **`rapidocr`**（`pharmacy_board2_node` + worker） | ROI、二值化、放大、文本规则 | **FREE 或 BUSY_5~10 任意 n** | **~1300 ms**（模型加载 +1630 ms） | 现场会出现非 8 秒；**ROS 2 车默认就是这条**（§15 第 21 条） |

> **先想清楚一件事**：如果比赛现场的板二**永远是"需等待 8 秒"**，用模板法最划算（快 30 倍、CPU 低）。但只要出现 `5/6/7/9/10`，模板法就会播错、等错——**这是"动作错"而不是"识别错"，扣分更狠**。所以**先确认现场牌面**，再选路线。

### 20.3 路线 A：模板匹配的完整流程

#### 第 1 步：采数据（决定上限的一步）

**要采什么**：板二在你**实际停车点**的画面，覆盖真实变量。

| 维度 | 要覆盖 |
|---|---|
| 状态 | `FREE` 至少 10 张、`BUSY_8` 至少 10 张（数字不同的也各采几张，用于验证"会不会误判成 8"） |
| 距离 | 停车点 ±10 cm 各一组（车不可能每次停得一样准） |
| 角度 | 车头偏左/偏右各 ±10°（斜视是最常见的失败原因） |
| 光照 | 白天/开灯/关灯各一组（曝光变化会让模板直接失效） |

**怎么采**：

```bash
# 方法 1：iscc gray 手动存（最简单）
iscc gray
#   画面里按 s 存 PNG，按 q 退出
#   注意：键盘焦点要在窗口上，终端里按键无效（历史踩过）

# 方法 2：抓帧脚本（批量，推荐）
#   写一个 rclpy 订阅 /camera/rgb/image_raw、每 0.5 s 存一张 PNG 的小脚本
#   ROS 1 用 cv_bridge(imgmsg_to_cv2(msg,'mono8'))；ROS 2 同理
#   存到 ~/board2_train/<free|busy>/ 下，文件名带时间戳
```

**采数据的三条纪律**
1. **别用"识别成功那一次"的图当模板**——要用**分布**（不同距离/角度）。
2. **把"废图"也留着**（黑图、空场景、墙、手挡一半），用来验证"会不会误报"。
3. **记下每张图的拍摄条件**（距离/角度/曝光），否则出了问题没法复现。

#### 第 2 步：做模板

**C++ `fixed` 要两张整牌图**：`assets/board2/pass.png`（FREE）、`assets/board2/wait8s.png`（BUSY_8）。
它会先把牌**透视矫正到 240×160**，再取两行文字条（192×40）做归一化互相关。

**Python `template` 要"一族"图**：`assets/board2_template/IDLE_*.png`、`BUSY_*.png`（现在 2+2 张）。多个模板时取**最大相似度**。

> 模板怎么选：**从采集集里挑"最典型"的 2~3 张**（正对、清晰、曝光正常），不要挑"最完美"的单张（会过拟合）。
> 换模板后**必须重启服务**：`sudo systemctl restart eprobot-pharmacy`（模板是启动时加载的）。

#### 第 3 步：调阈值（只有 4 个，别乱加）

| 参数 | 默认 | 调大的效果 | 调小的效果 | 什么时候动 |
|---|---|---|---|---|
| `min_score` | 0.60（Python）/ 0.72（C++） | 更严，拒识变多，误报变少 | 更松，能认出来但可能认错 | 现场"认不出"→ 降 0.05 试；"乱认"→ 升 0.05 |
| `min_margin` | 0.10 | 要求两状态差距更大，更保守 | 容易在"模棱两可"时下结论 | 两个状态长得像时**必须升** |
| `min_white` | **0.0**（本车）/ 0.50（库默认） | 要求牌更白 | 允许偏色 | **本车画面偏绿，白牌 S≈140**，所以必须 0.0，否则连牌都找不到 |
| `retry_upscale` | 2.0 | 远处小牌更容易找到（代价：多 70 ms） | 快，但远距离失效 | 停车点偏远时用；停了很近可以降到 1.0 |

**C++ `fixed` 还有 5 个隐藏阈值**（在 `board_classifier.hpp:10-23`，改要重编译）：
`min_primary_score 0.90`、`min_line_score 0.68`、`min_character_score 0.45`、`min_digit_score 0.66`、`max_digit_local_loss 0.035`。
其中 **`min_digit_score` 是专门用来分辨 "8" 的**（靠"8 字两个孔"的几何证据，3 档阈值至少 2 档同时检出上下孔才算）。

#### 第 4 步：批量回放验证（**不要一张一张看**）

仓库里有现成的基准工具：

```bash
# Python 模板后端的 bench（在仓库 pharmacy_pkg/test/ 下）
python3 board2_template_bench.py --help

# C++ 分类器的 benchmark（车上二进制）
/opt/eprobot_ws/install/pharmacy_pkg/lib/pharmacy_pkg/board_benchmark --help
#   历史数据：benchmarks/board2/final_fast.jsonl、final_full.jsonl
```

**验证集要留出来**：采 30 张，**20 张调阈值、10 张只用来验**。用调参那 20 张选出来的阈值，在剩下 10 张上的表现才是真实水平。

**输出三张表**（这就是你的"训练报告"）

| 表 | 内容 |
|---|---|
| 混淆矩阵 | 真实\预测：FREE / BUSY_8 / UNKNOWN（拒识） |
| 拒识率 | `UNKNOWN` 占比。**宁可拒识，不要认错**——认错会导致播错、等错、扣分 |
| 耗时分布 | p50 / p95 / max。p95 必须 < `board2_timeout`（ROS1 6 s / ROS2 8 s） |

**合格线（经验值）**
- 正确率 ≥ 95%
- **误判率（把 FREE 认成 BUSY，或反之）≤ 1%**
- p95 耗时 ≤ 200 ms（模板）/ ≤ 2.5 s（OCR）

#### 第 5 步：装到车上并现场验收

```bash
# 1) 放模板（记得备份旧的）
sudo cp -p /opt/eprobot_ws/install/pharmacy_pkg/share/pharmacy_pkg/assets/board2/pass.png{,.bak_$(date +%s)}
sudo cp ~/board2_train/new_pass.png /opt/eprobot_ws/install/pharmacy_pkg/share/pharmacy_pkg/assets/board2/pass.png
sudo chown keyuan22:keyuan22 /opt/eprobot_ws/install/pharmacy_pkg/share/pharmacy_pkg/assets/board2/pass.png

# 2) 重启识别服务
sudo systemctl restart eprobot-pharmacy

# 3) 验收：连做 10 次，全对才算过
#    并用真实的 5/6/7/9/10 秒牌各试一次（模板法在这里必然错，是预期行为）
```

### 20.4 路线 B：OCR 的"训练"流程

OCR 没有模板，改的是**预处理 + 后处理规则**。

```bash
# 1) 直接拿 worker 单跑一张图，看它输出了什么
echo /home/keyuan22/board2_train/busy6.png | /home/keyuan22/board2_ocr/run_worker.sh
#   期望输出：BUSY_6

# 2) 看 OCR 原始文本（worker 里 parse 之前的那一步）
#    临时加一行打印 res，或写个小脚本直接调 RapidOCR
python3 -c "
from rapidocr_onnxruntime import RapidOCR
ocr = RapidOCR(config_path='/home/keyuan22/board2_ocr/models/...')
res,_ = ocr('/home/keyuan22/board2_train/busy6.png')
print([r[1] for r in (res or [])])
"
```

**后处理规则在哪改**：`board2_ocr_worker.py` 的 `parse()`（正则 `等待(\d{1,2})`、`空闲`、`通过`、`忙碌`）。这是**唯一该改的地方**，别去改模型。

**四种典型失败与对策**

| 现象 | 原因 | 对策 |
|---|---|---|
| OCR 输出空 | 字太小 / 太糊 | 放大 2× 再送；或车停近一点 |
| 输出乱码 | 反光、过曝 | 降曝光（`iscc gray` 里 `-`）；或先做直方图均衡 |
| 数字认错（6→8） | 字体细/分辨率不够 | 只取"等待"后面两位数字做 ROI + 放大 |
| 把"空闲"认成"忙碌" | 关键字误匹配 | 收紧 `parse()` 的优先级：先判"空闲/通过"，再判"等待 n 秒" |

### 20.5 六个坑（都是真的踩过）

1. **模板法只会输出 `BUSY_8`**。换模板也改不了——它的标签是闭集（`pass.png→FREE`、`wait8s.png→BUSY_8`）。
2. **`template` 后端有个"编造"兜底**：认不出来就返回 `fallback_state=FREE`。看起来"从不失败"，其实是在赌。要"宁可不说话"就把 `fallback_state` 设成 `NONE`。
3. **曝光一变，模板全废**。同一块牌，曝光 40 和 200 拍出来是两个东西。**换模板前先固定曝光**（`iscc-cam-apply 40`），或者把两种曝光都采进模板族。
4. **不同车 / 不同相机不能共用模板**。`.22` 是 Astra S（无 UVC），`.21` 是 Astra Pro HD（有 UVC），色彩响应完全不同。`BOARD2_PORT_REPORT.md` 里就记着"卡上相机白平衡正常，本车画面整体偏绿"。
5. **斜视必须**进训练集。`BOARD2_PORT_REPORT.md` 明确写了：本车两张斜视图**原版 0/2**，必须 `min_white=0` + 2 倍放大才 2/2。
6. **改完模板要重启服务**（模板是启动时加载进内存的），否则你会以为"改了没用"。

## 21. IMU：干什么用、怎么换新的

### 21.1 IMU 在这套系统里解决什么问题

三件事，按重要性排：

| 作用 | 说明 | 不用它行不行 |
|---|---|---|
| **提供绝对朝向（yaw）** | 轮式里程只有"轮子转了多少 + 舵机打了多少度"，**没有任何绝对方向参考**。直线跑 10 m 后 yaw 会漂几度，转弯多几圈会漂十几度 | 行，但 AMCL 要更依赖激光匹配，转弯后位姿抖动明显 |
| **提供角速度（gyro）** | 转弯瞬间的角速度变化比"轮速推算"快得多 | 行，但急转时 EKF/预测会滞后 |
| **提供加速度** | 纵向加速度可用于估计打滑/坡道 | 基本不用（ROS 1 只用了 `ax` 一位） |

**一句话**：**IMU 让"车知道自己朝哪"，没有它车只知道"自己走了多远"。**

**两台车的用法不同**

| 车 | IMU 怎么进系统 |
|---|---|
| ROS 1（`.24`） | `/imu_data`（yaw）+ `/imu/data_raw`（ax）→ **EKF** 融合 → `odom→base_footprint`（`ekf_params.yaml`，§5.5） |
| ROS 2（`.22`） | `eprobot-imu` 发 `/imu/data` → **Nav2/AMCL** 直接用；`iscc` 还会检查 `yaw_source_used == h30`（`AGENTS.md` §10.4） |

**为什么 `iscc pre` 要专门检查 IMU**：底盘固件自己也能算一个 yaw（`0x0a` 回包里的），但那是**轮式+陀螺融合的粗糙版本**；H30 是独立的高精度模块。`yaw_source` 用错源，表现为"直线跑偏、转弯过冲"，而且很难从日志看出来。所以 `iscc-imu-check` 会专门验证"yaw 到底来自谁"。

### 21.2 现有硬件（`.22` 实测）

```
# udev 规则
# WHEELTEC H30 IMU (CH343 single serial, 1a86:55d4)
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d4",
  ATTRS{serial}=="5C98182597", SYMLINK+="EPRobot_imu", MODE="0666", GROUP="dialout"

# 设备
/dev/EPRobot_imu -> ttyACM0   (crw-rw-rw- root:dialout)

# 驱动配置 /opt/eprobot_ws/install/yesense_std_ros2/share/yesense_std_ros2/config/yesense_config.yaml
yesense_pub:
  ros__parameters:
    serial_port: "/dev/EPRobot_imu"
    baud_rate: 460800
    frame_id: "imu_link"
    driver_type: "ros_serial"
    imu_topic_ros: "/imu/data"
    publish_vendor_topics: false

# unit
eprobot-imu.service:
  ExecStart=... ros2 launch yesense_std_ros2 yesense_node.launch.py
  Environment=LD_LIBRARY_PATH=/opt/eprobot_ws/install/serial/lib
  Environment=ROS_DOMAIN_ID=1
```

**关键点**：它是 **USB 转串口（CH343，`1a86:55d4`）**，不是 SPI/I2C。所以"换 IMU"在系统层面就是**换一个 USB 串口设备 + 换一套驱动配置**。

### 21.3 换新 IMU 的 7 步

#### 第 1 步：插上，先看系统认不认

```bash
lsusb | grep -i -E "1a86|ch34|cp210|ftdi"   # 看 VID:PID
dmesg | tail -20                            # 看是不是 CDC-ACM，有没有报错
ls -l /dev/ttyACM* /dev/ttyUSB*
```

**三种常见芯片**：CH343（`1a86:55d4`）、CP210x（`10c4:ea60`）、FTDI（`0403:6001`）。**不同芯片的 driver 不同，但都是 `/dev/ttyUSB*` 或 `/dev/ttyACM*`。**

#### 第 2 步：拿到"唯一标识"，写 udev 规则

**不要抄别人的序列号**——`AGENTS.md` §2.2 记着一条真实事故：`.21` 的 H30 序列号是 `5C2C063393`，`.22` 是 `5C98182597`，**直接拷规则会匹配不上 → `/dev/EPRobot_imu` 根本不出现**。

```bash
# 拿序列号（三种方式，任选）
udevadm info -a -n /dev/ttyACM0 | grep -E "idVendor|idProduct|serial"
ls /dev/serial/by-id/          # 最直观：直接给出含序列号的符号名
cat /sys/class/tty/ttyACM0/device/../serial 2>/dev/null
```

```bash
# 写规则（把 serial 换成你自己的）
sudo tee /etc/udev/rules.d/99-eprobot-imu.rules >/dev/null <<'EOF'
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d4", ATTRS{serial}=="你的序列号", SYMLINK+="EPRobot_imu", MODE="0666", GROUP="dialout"
EOF

sudo udevadm control --reload-rules
sudo udevadm trigger
# 拔插一次
ls -l /dev/EPRobot_imu      # 必须出现
```

> **为什么必须用序列号**：车上同时插着雷达（也是 USB 串口）、相机、可能的第二块串口板。只按 VID:PID 匹配，`/dev/EPRobot_imu` 可能指到雷达上——**这是最阴的一类故障**（IMU 数据变成激光数据）。

#### 第 3 步：改驱动配置

```bash
# 备份
sudo cp -p .../yesense_config.yaml .../yesense_config.yaml.bak_imu_$(date +%s)

# 改三处：串口、波特率、frame_id
sudo nano .../yesense_config.yaml
```

| 字段 | 怎么定 |
|---|---|
| `serial_port` | `"/dev/EPRobot_imu"`（跟着 udev 符号走，别写死 `ttyACM0`——插拔顺序会变） |
| `baud_rate` | **看新 IMU 手册**。H30 是 `460800`；很多模块是 `115200` 或 `921600`。**错了就是一个字节都收不到** |
| `frame_id` | `"imu_link"`（要和 TF 树里的静态 TF 子帧名一致，§6.4） |

**如果新 IMU 不是 Yesense 协议**：`yesense_std_ros2` 用不了，得换驱动包（常见的是 `wit_ros2_imu`、`fdilink_ahrs`、`hipnuc_imu`）。这时候改的是 **unit 的 ExecStart**，不是 yaml。

#### 第 4 步：起服务并看日志

```bash
sudo systemctl restart eprobot-imu
systemctl status eprobot-imu --no-pager
journalctl -u eprobot-imu -n 50 --no-pager
```

**典型报错对照**

| 日志 | 原因 |
|---|---|
| `cannot open /dev/EPRobot_imu` | udev 没生效 / 序列号写错 / 权限不足 |
| `open success` 但没有数据 | **波特率错**（最常见）/ 线序（TX/RX 反） |
| `checksum error` 刷屏 | 波特率接近但不对（比如 460800 vs 921600） |
| `no such device` 且 `dmesg` 有 `device descriptor read error` | 供电不足（Pi 的 USB 口带不动）→ 换口/加供电 Hub |

#### 第 5 步：验证数据（三条判据，缺一不可）

```bash
# 判据 1：频率对不对
ros2 topic hz /imu/data
#   H30 期望 100 Hz 左右（ROS 1 车实测 /imu/data 约 245~299 Hz 是另一套 0x0a 回包；
#   ROS 2 的 H30 是独立模块，按模块标称值核对）

# 判据 2：静止噪声（陀螺零偏）
ros2 topic echo /imu/data --field angular_velocity --once   # 停 10 秒，看 z 是否接近 0
#   静止时 |wz| 应 < 0.01 rad/s；一直 0.05 以上说明零偏没标定

# 判据 3：朝向与实际一致（最容易被忽略）
#   把车头摆到"已知方向"（比如正对 +x），看四元数解出来的 yaw 是不是 0
ros2 topic echo /imu/data --field orientation --once
#   反了就说明安装方向/坐标约定不对，要么转 180°，要么在驱动里配 yaw 偏移
```

#### 第 6 步：标定安装偏移（`imu_link` 的静态 TF）

`nav2_bringup.launch.py` 里写的是 `base_link → imu_link (0.08, 0, 0)`（实测）。**换 IMU 位置变了就要改这个值**，否则 EKF/AMCL 会把"IMU 装在别处"当成"车在别处"。

```python
# launch 里改这一行
_static_tf("base_to_imu_tf", ("0.08", "0.0", "0.0"), "imu_link")
```

量法：卷尺从 `base_link` 原点（通常在后轴中心地面投影）量到 IMU 芯片中心，x 向前、y 向左、z 向上。

#### 第 7 步：端到端验证（跑起来才算数）

```bash
iscc pre            # 看是否打印 "ok (h30 drives yaw)"
# 或者
sudo -n timeout 15 /usr/local/bin/iscc-imu-check
```

**最低限度**：`iscc status` 里 `--- imu ---` 那行有频率、`yaw_source` 正确。

### 21.4 五个坑

1. **序列号写错/抄别人的** → 设备节点不出现，或者指向别的串口设备。
2. **两个 IMU 抢一个符号**：新旧 IMU 同时插着，udev 规则都匹配 → 谁先枚举谁占，数据忽好忽坏。**换的时候把旧的拔掉。**
3. **坐标系方向反了**：表现为"车左转，IMU 说右转"，AMCL 会越跑越偏。**先静止验证朝向，再跑导航**（§21.3 第 5 步判据 3）。
4. **树莓派没有 RTC**：IMU 数据带的是"系统时间"，时钟一跳，TF 就对不上（§6.7 地雷 2）。**换完 IMU 顺带校时**。
5. **`dialout` 组**：`MODE=0666` 已经放开权限，但如果你的规则里漏了 `MODE`，非 root 用户读不到串口，症状是"服务起来了但没数据"。

## 22. 导航调参决策表 + CPU 算力分配

### 22.1 先建立因果链（调参前必须知道自己在动哪一环）

```
目标点 (x,y,yaw)
   ↓ ① 全局规划（ROS1 navfn / ROS2 Smac Hybrid）
全局路径
   ↓ ② 局部规划（ROS1 TEB / ROS2 MPPI）+ 代价地图
/cmd_vel（线速度 + 角速度）
   ↓ ③ 底盘换算（δ = atan(L·ω/v)）+ 串口协议
轮速 / 舵机角
   ↓ ④ 里程计（odom）+ EKF + AMCL
定位
   ↓ 喂回 ① ②
```

**四条诊断铁律**
1. **车不动** → 先看 `/cmd_vel` 有没有数；有数看底盘/串口，没数看 ①②。
2. **车走偏/画龙** → 先看 ④ 定位准不准（RViz 里激光和墙重合吗），再谈 ②。
3. **到点不准** → 是"停早了/停晚了"（②/到点容差）还是"根本没到那"（①/点位本身）。
4. **某个点总失败** → 90% 是**几何**问题（余量、转弯半径、朝向），不是参数问题。先量距离，再调参。

### 22.2 "想改善 X 就改 Y"（按诉求查）

| 你想要 | 改什么 | 怎么改 | 依据 |
|---|---|---|---|
| **别冲过头** | 限速节点 `target_stop_radius` / `slow_speed` | 把目标点的 stop 半径加大（0.35→0.65） | `goal_speed_limit.py`，§6.6 |
| 冲过头（局部） | MPPI `vx_max` / `ax_min` | 1.2→0.9；-3.0→-2.0 | `nav2_params.yaml` |
| 冲过头（ROS1） | TEB `max_vel_x` / `acc_lim_x` | 0.9→0.6；1.0→0.8 | `teb_local_planner_params.yaml` |
| **到不了框** | 目标点坐标 | 挪点（**先量余量 ≥ 0.20 m**） | 半对角 0.182（ROS1）/0.186（ROS2） |
| 到不了框（窄处） | `inflation_radius` | 0.28→0.22（ROS2）/ 0.20→0.15（ROS1 全局） | 膨胀越小越贴墙，但更容易蹭 |
| 到不了框（朝向） | `yaw_goal_tolerance` / `free_yaw_targets` | 0.35→0.6；或把该点加进 `free_yaw_targets` | §15 第 22 条 |

| **定位飘** | AMCL `update_min_d/a` | 0.1→0.05（更新更勤） | 更准但更吃 CPU |
| 定位飘（ROS2） | `transform_tolerance` | 0.5→1.0 | 太小会 `queue is full` |
| **起步猛冲** | 首圈限速 | ROS1 已在 `read_task()` 里做（0.35/0.5） | |

### 22.3 参数方向与副作用（调之前先看这一列）

| 参数 | 调大 | 调小 | 主要副作用 |
|---|---|---|---|
| `vx_max` | 更快 | 更稳 | 太大 → 冲过框、转弯离心 |
| `ax_max` | 起步更猛 | 更肉 | 太大 → 打滑，里程虚高 |
| `ax_min`（刹车） | 刹得更狠 | 更缓 | 太狠 → 点头、丢定位、轮子打滑 |
| `wz_max` | 转得更快 | 更稳 | 太大 → 画龙、阿克曼转不过来 |
| `inflation_radius` | 更怕墙、绕远 | 更贴墙 | 太小 → 蹭墙/卡死；太大 → 窄通道无解 |
| `min_turning_radius` | 只走大弧 | 允许急转 | 小于物理极限 → 规划出转不出来的路径 |
| `xy_goal_tolerance` | 容易判"到了" | 停得更准 | 太大 → 没进框就算成功（丢分） |
| `yaw_goal_tolerance` | 容易判"朝向对" | 收尾更严 | 太小 → 原地磨、`Failed to make progress` |
| `required_movement_radius` | 容忍原地磨 | 更快判失败 | 太大 → 卡住了也不救；太小 → 正常调整被误判 |
| `transform_tolerance` | 容忍时钟/TF 延迟 | 更实时 | 太大 → 位置滞后；太小 → 丢帧报错 |

### 22.4 两条铁律（重复三遍不算多）

1. **一次只改一个参数**，改完必须实车跑同一个场景（同一个起点、同一个目标）。
2. **判据要可量化**：不看"好像好点了"，看 `mission.jsonl` 里的段耗时、`delivered` 前后的距离、`navigation_failed` 次数。

### 22.5 CPU 算力分配（Pi 4B 只有 4 核，很紧）

#### 先看实测基线（`.22`，2026-11-13 21:00 采样）

| 进程 | CPU | 说明 |
|---|---|---|
| `unattended-upgrade` | **83.0%** | **系统自动更新在跑！**（我当时看到的就是这个） |
| `dpkg` | 17.9% | 同一次更新的解包 |
| `openni2_camera_driver` | 37.9% | 相机取流（rgb8 921 KB/帧） |
| `yesense_node_publisher` | 19.9% | H30 IMU |
| `mono8_relay` | 11.5% | C++ 灰度转换（`max_fps 10`） |
| `eprobot_base` | 10.4% | 底盘驱动 |

**load average 2.68（4 核）**、CPU 1.8 GHz、温度读不到（`vcgencmd` 报 `Can't open device file: /dev/vcio`，见下方）。

**结论：光"底盘+IMU+相机"就吃掉约 80% 单核**。再叠 Nav2 + 识别 + 语音，很容易饱和。

#### 15 条省 CPU 的具体做法（按性价比排序）

| # | 做法 | 能省多少 | 怎么做 |
|---|---|---|---|
| 1 | **关掉自动更新** | **最大头**（实测 83%） | `sudo systemctl disable --now unattended-upgrades apt-daily.timer apt-daily-upgrade.timer` |
| 2 | **只开需要的相机流** | 相机 42%→13% | ROS1：`depth_registration:=false`、`depth_processing:=false`、`ir_processing:=false`、`sw_registered_processing:=false`、`num_worker_threads:=2` |
| 3 | **relay 限帧** | relay 53.7%→8.5% | `ISCC_MAX_FPS=15`（实测值）；只需要 QR/板二时 10 也够 |
| 4 | **用 C++ relay 替 Python** | 30%→13%，内存 117→77 MB | `mono8-relay.service`（已是 C++） |
| 5 | **板二按需订阅** | 空闲 ~25-30%→0% | `/pharmacy/board2_control` 为 `true` 才订阅图像，`false` 立刻退订 |
| 6 | **QR 降扫描频率** | 线性 | `detect_qrcode.scan_hz: 5.0`（别设 30） |
| 7 | **别在生产挂诊断脚本** | 19~44% | `live_monitor` 那种 10 Hz `ps` 的脚本，只在排障时开 30~60 秒 |
| 8 | **`ros2 topic hz` 别常开** | 视话题 | 它自己是订阅者，会唤醒 `BEST_EFFORT` 发布者（相机/深度） |
| 9 | **车上别开 RViz** | 很大 | RViz 走软件渲染；要看就在 WSL 里看（§6.7 地雷 3） |
| 10 | **关掉不用的 unit** | 每个 5~20% | `image-relay`（旧 Python 版）、`camera-shim`、`nav-tune-web`、`scan-viz`（不给远程看时） |
| 11 | **`nice`/`ionice` 抓包** | 避免抢 CPU/IO | `car_bag.sh` 已经用 `nice -n 10 ionice -c2 -n7` |
| 12 | **清 SHM** | 起不来/飙高的元凶 | `ls /dev/shm \| grep -c fastdds`，多了就 `iscc kill`（§6.7 地雷 1） |
| 13 | **降控制频率** | 线性 | `controller_frequency 10→8`（代价：跟踪变粗） |
| 14 | **MPPI 降采样** | 明显 | `batch_size 1000→600`、`time_steps 30→24`（代价：轨迹略糙） |
| 15 | **`taskset` 绑核**（进阶） | 减少抖动 | `taskset -c 0,1 ros2 run ...`（把 nav 钉在两个核，视觉钉在另外两个） |

#### 温度与降频（`vcgencmd` 在这台车上用不了）

实测 `vcgencmd measure_temp` 报 `Can't open device file: /dev/vcio`（缺 `vchiq` 设备）。替代方案：

```bash
# 温度（摄氏度）
cat /sys/class/thermal/thermal_zone0/temp | awk '{printf "%.1f °C\n", $1/1000}'
# 当前频率（Hz）
cat /sys/class/cpufreq/policy0/scaling_cur_freq 2>/dev/null || \
  cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq
# 是否降频（需要 vcgencmd 时才准；不可用就看上面的频率有没有掉到 600 MHz）
```

**判据**：频率长时间低于 1.5 GHz = 在降频 = 散热不行。Pi 4B 过热会掉到 600 MHz，那时导航会突然"变傻"。

> 如果一定要用 `vcgencmd`：`sudo mknod /dev/vcio c 100 0 && sudo chmod 666 /dev/vcio`（⚠️ 这会改系统设备节点，属于"改配置"，按 §0.4 的规矩要先确认）。

#### 一个反直觉的点：load average 会骗人

实测 load 2.68（4 核）但 CPU 并不满——**因为 `unattended-upgrade` 在等 IO**。load 包含"不可中断睡眠（D 状态）"，所以：

```bash
# 看 CPU 真实占用（不是 load）
top -bn1 | head -12
# 看谁在等 IO
ps -eo stat,pcpu,comm | awk '$1 ~ /D/'
```
